## Open units of work

### EW-01: An IME composition over a block selection writes its preview into the first paragraph, and the stray text is saved

- **Area:** Editing behaviors
- **Severity:** high
- **Effort:** M
- **File:** src/lib/surface/projector.svelte.ts:349 (also composition.svelte.ts `start()`, around :149)
- **Failure:** While a block selection is shown, the projector clears the DOM range (rangeCount 0). `composition.start` sets `host = null`, and nothing places the native selection before the IME writes. Chromium then puts the composition at the start of the editable, and the mutation observer adopts it into the first Text. This was reproduced with the CDP IME driver on `/test/dom?scenario=divider`:
  - Mod+A twice, compose 'に', commit '日' gives `['にbefore divider', '', '日']`.
  - Backspace-selecting the divider, then compose and commit, gives `['にbefore divider', '日', 'after divider']`.
  - Both cases need 3 undos to restore the document. A plain caret gives one clean step.
  - The stray character is synced and saved, possibly off-screen.
  - selection.mdx:117 promises that 'a composition … replaces the selected blocks'.
  - Small correction to the original report: in the Mod+A case the selected block itself became '日', rather than a new block being added.
- **Fix:** Keep a DOM range the IME cannot write through while a block selection is shown. For example, use a collapsed range inside the first selected block's line. Alternatively, on compositionstart with `selectedBlocks`, run `flow.slot` first and move the native selection into the new empty block before the first update. Also reject a mutation-observer adoption outside the composition's own slot.
- **Done when:** An ime-baseline CDP row covers a composition over Mod+A×2, over a Backspace-selected divider and over a Shift+↓-selected void. Each row asserts that the first paragraph is unchanged, that the composed text replaces the selection, and that one undo restores the blocks.

### EW-02: Ranking every insert and move by source makes ranks and documents grow several times faster

- **Area:** CRDT correctness and Code organization (counted in both)
- **Severity:** medium
- **Effort:** M
- **File:** src/lib/crdt/placement/model.ts:573 (`lineageOf`), :604 (`belowOf`) and `place`/`sourceRanks` around :649; src/lib/crdt/edytor-doc.ts:1658-1691 (`ranksFor`)
- **Failure:** `lineageOf` and `belowOf` only collapse chains that run in one direction. Any interleaving nests one level deeper, and `place` rescans every sibling rank for each choice. All measurements below compare the working tree with a git-archive copy of bf87634, on a single replica through the facade:
  - **Random caret walk** (2,000 steps; 40% Enter at the end, 40% Enter at the start, 20% arrow keys): max rank 1,664 characters against 144, and 1.6 MB against 549 KB.
  - **Local random walk** (400 Enters near the caret): mean/max 546/864 characters against 123/208, and 323 KB against 154 KB.
  - **3,000 one-step reorders of 20 lines:** mean rank about 6.6 KB against 23 characters, and 10.26 MB against 148 KB.
  - **'Enter twice from the newest line':** 1.4 s for one Enter after 200 steps (against 1 ms). The 400-step run did not finish in 600 s.
  - **Strict start/end zigzag:** it already grew linearly at bf87634. Wave 13 doubled the slope rather than introducing the growth.
  - docs/editor-delete-contract.md:586 ('Ranks stay a few levels deep however lines and outlines are typed') is false as written. The dw-followup `flat` rows cover only one-direction chains.
  - Text order and convergence are unaffected.
- **Fix:**
  - Bound the depth. When the anchor chain beside the gap is more than k levels deep, or the rank would exceed a byte budget, fall back to `clusterBase` (a fresh key between the neighbours) and name that case as an ordering residual.
  - When the gap has a piece chain on one side and a below chain on the other, rank from the shared outer base.
  - Keep moves on plain ranks (`M.ranksAt`), since concurrent moves are already outside the order claim.
  - Scan the siblings once per call instead of once per choice.
  - Narrow contract :586 to the patterns that are tested.
- **Done when:** dw-followup has `flat` rows for the alternating start/end zigzag, a seeded 1,000-step caret walk, 'Enter twice from the newest line' and 3,000 reorders. Each row keeps ranks under BOUND (209 characters), with the length at 300 steps equal to the length at 40. The 3,000-reorder document stays within a small multiple of the bf87634 size, per-Enter latency stays flat, and the contract line matches what is tested.

### EW-03: Tab into a block is ranked as a piece of its last child, so an outline race breaks the text order on half the client-id pairs

- **Area:** CRDT correctness
- **Severity:** medium
- **Effort:** M
- **File:** src/lib/crdt/edytor-doc.ts:1668-1672 (childless-parent fallback at :1679; `nestBlock` at :2745-2748)
- **Failure:** Tab runs `nestBlock`, which calls `moveBlocks` to `{parent: x, index: children.length}`. `ranksFor` then gives `pieceRanks(k, displayLength(k))`, the same rank family as a concurrent Enter at the end of k, so only the client id orders them.
  - Setup: x has child k, and y follows x. Ada presses Tab on y while Bob presses Enter at the end of k and types N.
  - Result: `{x|k|y|N: 24, x|k|N|y: 24}` for both paragraphs and directly nested list items. The serial order is x|k|N|y.
  - A list whose item holds a nested list is not affected.
  - Contract :557 lists Tab among the moves 'ranked by where it goes', :589 leaves Tab out of 'Not claimed', and concurrent-editing.mdx:179 says 'not at random'.
  - No sweep row covers Tab.
- **Fix:** Rank a nest or append at a parent's end as a block that ends the parent (an end-of-parent side after every piece of the last child), and use a fixed base rather than `M.ranksAt` for a childless parent. Otherwise, name Tab in the 'Not claimed' lists of contract :589 and concurrent-editing.mdx:179 and fix the `ranksFor` comment.
- **Done when:** dw-order-sweep rows for 'Tab y ‖ Enter at the end of x's last child' (paragraphs and list items) keep the serial order on all 240 pairs, and the toggle mid-split row and the childless row are decided. Alternatively, the contract and the site both list Tab as not claimed.

### EW-04: A peer's second Enter at the end of the same block counts its own earlier typed line as that block's text

- **Area:** CRDT correctness
- **Severity:** medium
- **Effort:** M
- **File:** src/lib/crdt/edytor-doc.ts:1813-1830 (`pieceRanks` tail; `lineageOf`'s `end`)
- **Failure:** `tail` includes every sibling after X whose rank starts with anchor+PIECES, including lines that `insertBlockAfter` placed after X.
  - Seed `[P, X 'hello world', Q]`. Bob presses Enter at the end of X and types 'a longer line', then presses Enter at the end of X again and types 'bar'. Concurrently, Ada splits X at 5.
  - Result: `P|hello|bar| world|a longer line|Q` on 240/240 pairs. Bob's part is 11-24 = -13 against Ada's 5-11 = -6.
  - The order is correct when Bob's first line is shorter than ' world', and when his first line is empty.
  - Contract :578-583 claims DW-02 covers 'typing a line and pressing Enter again'. The tested rows only press the second Enter at the end of the new line.
- **Fix:** Exclude blocks inserted after X (part-0 or insert-after lineage members) from `tail`. For example, give an insert-after its own part at the block's end that never adds to the lineage length.
- **Done when:** A DW-02 row ('Enter at the end of X, type a line longer than the other peer's tail, Enter at the end of X again ‖ mid split of X') keeps `hello| world|bar|a longer line` on 240 pairs.

### EW-05: Docs promise that several edits per peer before sync keep the text order, but Enter-at-end then split, or Duplicate then split, reorders it

- **Area:** Documentation (the root cause is a CRDT gap in the same family as EW-04: an edit-placed neighbour inside a block's piece lineage)

- **Effort:** M

### EW-06: Escape on a lone selected divider leaves the model caret inside the divider

- **Area:** Editing behaviors
- **Severity:** medium
- **Effort:** S
- **File:** src/lib/session/bindings.ts:291-298 (`selectedBlocksLine` in replaceSelection.ts:151; `selectBlocks()` in selection.svelte.ts:1315-1323)
- **Failure:** With only a divider selected, `selectedBlocksLine` returns undefined. Escape then calls `selectBlocks()` with no arguments, which turns the selection into a text value on the divider's phantom text.
  - In jsdom: `[first, middle, divider, after]`, caret at the start of 'after', Backspace (selects the divider), Escape, type 'Z'. The result is `{type:'divider', content:[{text:'Z'}]}`, an invisible-content shape.
  - The reviewer's Chromium run shows the text landing at the start of the first paragraph and a paste being dropped. That run was not repeated during verification.
  - Wave 13 makes this state easier to reach (SW13-keys-2 and DR-behavior-1 leave a divider selected). Enter has a void-only branch; Escape does not.
- **Fix:** In the escape binding, when `selectedBlocksLine` is undefined, put the caret on the nearest shown line after the selected voids, or else the one before it. Keeping the divider selected is the other option. Never call `selectBlocks()` without arguments over voids alone. Update hotkeys.mdx:50 and selection.mdx:117 for the lone-void case.
- **Done when:** A DOM row (Backspace selects the divider, Escape, type) puts the text in the neighbouring line and leaves the divider's content empty. A Chromium row confirms that typing, Enter and paste land there.

### EW-08: onDeleteSelectedBlocks docs say an emptied code block goes with the deleted blocks

- **Severity:** low
- **Effort:** S
- **File:** src/lib/plugins.ts:150-153 (also site/content/docs/plugins/writing-plugins.mdx:193)
- **Failure:** A code block is an island, and `isContainer` excludes islands (edytor-doc.ts:1169-1170), so it is never auto-removed.
