`DocumentRoom` is a Durable Object that coordinates one document: deploy one object per document, reached through [`routeDocumentSocket`](/docs/server/authorization). This page describes what the room checks on every message, how it stores the document, and the settings and limits you can tune.

:::note
Everything on this page also holds for a document attached to your own Durable Object with [`attachRoom`](/docs/server/extending); only its table names differ (`edytor_rows`, `edytor_replicas`, `edytor_meta`, and `edytor_epochs`, `edytor_editors`, `edytor_restore` for the [history and the purge](/docs/server/history)).
:::

## One room per document

`routeDocumentSocket(request, env.ROOMS, documentId, authorize)` opens the room named `documentId` (`env.ROOMS.getByName(documentId)`). The room keeps the live document in memory, stores it in the object's SQLite storage, and relays edits and presence between the sockets connected to it. Clients are the ordinary `createWebsocketSync` or `WebsocketProvider`.

## Admission

Every frame a socket sends is checked in this order. A refused frame is never applied, stored or relayed.

1. **Generation.** The frame's first word must be this build's generation (see [the protocol](/docs/server/protocol#frames)). A client of another edytor generation is refused before anything is decoded.
2. **Access.** An edit from a read-only socket is dropped with a `permission-denied` reply (`read-only`). The socket stays open. When it joins, it gets a read-only notice instead (auth subtype `1`), which is not a refusal.
3. **Identity.** Content an update adds under a client id owned by another user, or under an unregistered id that already has content, is stripped from the frame, and the rest of the frame is applied: the sender stays connected. See [replicas](/docs/server/authorization#replicas). So is a client's content when it writes another client's per-writer block mark (`del.<n>`, `wd.<n>`), and a delete of another user's mark is dropped (logged `mark`; see [validate edits](/docs/server/extending#validate-edits)).
4. **Schema.** An update that writes a foreign schema stamp is refused. The same check covers updates waiting for a missing dependency: when an update would release a waiting one that carries a forged stamp, the waiting updates are discarded, the new update is applied, and its sender stays connected. Honest updates discarded this way come back at their writer's next sync.

A refused socket is closed with code `1008` and reason `refused: <reason>` (`generation`, `replica`, `schema`, `malformed`, `identity`, `container`). Only bytes the room cannot decode, a text frame other than the keepalive `ping`, or an unknown message type count as `malformed`. A refusal is final: the provider stops dialing instead of reconnecting. The other closes a dial can get:

| Close | When | Final? |
| --- | --- | --- |
| `4403` | `authorize` denied the dial: it never reaches the room, `routeDocumentSocket` closes it (see [authorization](/docs/server/authorization#authorize)). | Yes |
| `4400` `invalid document id` | The id is empty, `.`, `..`, over 256 characters or with a lone surrogate; closed before `authorize` runs. | Yes |
| `4401` | `authorize` returned `{ expired: true }`. | No: the one `4xxx` code the provider retries, with the `params` it re-reads. |
| `4409` `replica bound to another user` | The dial's replica belongs to another user; the dial is accepted, then closed. | Yes |

A dial your own Worker turns away before `routeDocumentSocket` gets the same kind of close from `closedSocket(code, reason)`, never an HTTP error, which the browser reports as `1006` and the provider redials.

A write past a [quota](#quotas) is closed with `4413` and reason `quota: <name>`; it is not applied, and the provider stops dialing too.

A fault of the room itself is never a refusal. A storage error (writing a client-id registration, say) closes the socket with `1011` and reason `storage failure`; an error of the CRDT engine or of a send closes it with `1011` and reason `internal error`, after the live document is rebuilt from the stored rows. The provider redials, and the handshake resends what the room does not hold. A fault that persists (a full store, an update the engine cannot apply) does not make it redial every 100 ms: each `1011` doubles its backoff, and emits `unreachable`, until the room acknowledges its edits again.

## Identity and presence

- The socket's identity (`user`, `replica`, `readOnly`, `expiresAt`) is saved in the socket's attachment, so it survives hibernation.
- Each relayed presence state that names an actor names the socket's verified user as its `actor.id`, whatever the client wrote ([attribution trust](/docs/server/authorization#attribution-trust)).
- Presence is relayed without an `Awareness` instance (its timer would keep the object awake). A socket may publish presence only for its own client id; entries for other ids are dropped.
- A new socket receives the presence of everyone connected. A socket that closes without saying goodbye is announced as gone, also after the room woke from hibernation.
- An accepted presence entry is also sent back to its sender. A client alone in a room therefore hears from it at every presence renewal and is never closed as silent.
- Keepalive: the provider sends a text `ping` after 15 seconds of silence, and the room answers `pong` through the runtime's WebSocket auto-response (`ctx.setWebSocketAutoResponse`), without waking the object. The room installs the pair when it starts, unless your object already set one; it then answers `ping` from its message handler. The auto-response applies to every socket of the object, yours included.
- The presence snapshot lives in memory. After a wake it refills as clients renew their presence, every 15 seconds.
- Presence has quotas of its own, which never close a socket (read-only sockets keep presence, within them):
  - An entry whose state, as JSON, is larger than `EDYTOR_MAX_PRESENCE_BYTES` (16 KiB) is ignored: not kept, not relayed, logged as a `presence` refusal (`{ user, quota: 'size', bytes, limit }`). The socket's previous entry stays.
  - Presence messages (entries and queries) draw from a token bucket of their own, `EDYTOR_MAX_PRESENCE_PER_SECOND` per socket (50, with a ten-second burst), apart from the sync messages' [update rate](#quotas). A view publishes at most every 50 ms, so only a misbehaving client reaches it. Past it, a query is dropped, and an entry is held: the socket's newest entry waits for the next token and is relayed at the end of any socket's next message (the room schedules no timer), with the other entries released then, in one frame. Both are logged `presence` (`{ user, quota: 'rate', limit }`), once per burst: the socket's first message past the rate is one entry, its next message within the rate ends the burst, and `refusalCounts.presence` counts every message past it.

## Storage

The room stores the document in its own SQLite tables ([Room internals](/docs/server/internals#storage-tables) lists them all, with the alarm's tasks):

- Every integrated update is appended as one record, split into rows under the platform's 2 MB row limit, in one transaction. Only then is it broadcast to the other sockets. Update records are stored in the v1 update encoding, the smaller one for an edit.
- A delete of an item the room does not hold yet (a deletion of text a restore lost, for example) is stored as a waiting record and applies when the item arrives. At most `MAX_WAITING_DELETES` (1,024) ranges wait: see [Waiting deletes](#waiting-deletes).
- After `EDYTOR_COMPACT_AFTER` update records (500 by default), the room replaces all rows with one snapshot of its live document (plus one record of the deletes still waiting: those that applied, and those reclaimed, are dropped), atomically, once the message that made it due is acknowledged. The snapshot is the document's healed state: what each keystroke wrote is merged and deleted content is collected, except text a peer's undo may copy back, which the room keeps as every editing replica does. It never includes updates still waiting for a missing dependency: they are stored when it arrives. On a real editing trace (`automerge-paper`, 259,778 edits) that is 1.6 MB instead of the 6.7 MB a merge of every stored update keeps, and a woken room loads it in about a sixth of the time. A compaction that fails is logged as a `storage` refusal and retried later; the edit is already stored and nobody is disconnected.
- The snapshot is stored in the compact (v2) update encoding, then gzip-compressed in place where the runtime has `CompressionStream` (Workers do): the trace above stores 224 KB. The compression runs after the compaction (it is asynchronous, the acknowledgement path is not) and rewrites the snapshot's rows only while they are still the stored snapshot; `compressed()` resolves once it is stored. A woken room inflates the snapshot before it accepts any message. The generation record carries the format (`storage: 'v2'`); a container written by an earlier pre-release (no `storage`: every record v1) loads as it is and its next compaction rewrites it in v2. A snapshot that does not inflate, or a format this build does not read, refuses every socket (`1008`, `refused: container`). A container compacted in v2 cannot be read by an earlier pre-release, which refuses it the same way.
- Memory never runs ahead of storage. If an append fails, nothing is relayed or acknowledged, the live document is rebuilt from the stored rows as a restart would, and the sender's socket is closed with `1011`. Its provider reconnects and the handshake resends the edit. If the append of the room's own edit fails ([`transact`](/docs/server/extending#edit-on-the-server)), `transact` throws the storage error and the edit is lost: nothing resends it. The room rebuilds from its rows too, but unlike after a client's failed append it keeps the updates it holds waiting for a missing dependency. A rebuild replaces the room's `doc` and `facade`. If reading the rows fails, during that rebuild or when the room starts, it has no document until a dial reads them again: sockets are closed with `1011` (`room unavailable`), their providers redial, and each dial retries the read.
- A woken room rebuilds the document from its rows before it accepts any message. A room whose rows read but cannot be restored (another edytor generation, a torn record) refuses every socket with `1008` and reason `refused: container`, and the object keeps answering. See [generation cutover](#generation-cutover).
- The client-id registrations used for [identity](/docs/server/authorization#replicas) are stored next to the document, and handed to [`onSave`](/docs/server/extending#save) with it. Compaction drops the registrations of ids that hold no content and belong to no open socket (a page that loaded and never wrote); such an id registers again at its next dial or write.
- Deleted content is kept for undo and for edits made concurrently elsewhere, then purged: content deleted more than 30 days ago (`EDYTOR_PURGE_AFTER_DAYS`) is removed from the rows and from every client by the room's own edit. A [version history](/docs/server/history) (two versions a day, in KV, R2, the room's own storage or a store of your own) keeps those 30 days restorable. See [History and purge](/docs/server/history).


### Waiting deletes

Any writer may delete any content, but storing deletes that wait adds durability and a per-update cost, which a bound caps. Every update the room applies re-reads the waiting deletes, so at most `MAX_WAITING_DELETES` (1,024) ranges wait.

- **Past the bound.** A frame whose deletes of unheld items would pass it has those deletes dropped, logged as a `waiting` refusal, and the rest of the frame applied. That includes deletes of the frame's own items that wait (for a missing origin) and the attribute values its waiting changes replace: when they take the room past the limit, all of the frame's new waiting deletes are dropped the same way.
- **The sender sees it.** The acknowledgement leaves the dropped deletes out, so the sender's `saved` stays `false` and its next connection resends them; until one is stored, the deleted content shows if its author returns.
- **How long one waits.** A waiting delete lasts until its item arrives, but compaction reclaims those of a client id that no user registered and no open socket holds (a made-up id: nothing can deliver its items), in memory too; the registrations of ids with waiting deletes are kept.
- **Registered ids are kept.** Deletes of a registered id's items are kept, as they may be a relayer's deletes of text its author will bring back, so a writer can still fill the limit with deletes of its own or another user's future items. Frames past the limit then keep logging `waiting` refusals: call [`dropWaitingDeletes()`](#compaction-over-rpc) to empty it.
- **Restores.** An author missing from the restored registry (a snapshot saved before that author first dialed, or a bare `update` with no `replicas`) is unknown until it dials again, so a compaction before then reclaims the deletes of that author's text. Waiting deletes arm [`onSave`](/docs/server/extending#save) like any edit, and a room restored from its `onSave` copy stores the waiting deletes it carries as a waiting record again, so they are acknowledged and reclaimed the same way.

**Edge cases.**

- The attribute value that an attribute change of the same update replaces, while that change itself still waits for a missing dependency, is not a waiting record: that delete waits with the change, in memory, so the attribute is never emptied.
- If a later update would make such a delete remove the schema stamp, every waiting delete is discarded (the room also drops a pending forged stamp that way).

## Store before acknowledge

Every sync message a client sends is answered, after the room has stored what it integrated, with a *saved* frame: the room's state vector and, when the message deleted content, the deletes of that message the room stored, applied or waiting for their items (never one it dropped or keeps in memory only). The provider turns these into its [`saved` and `unsaved` state](/docs/collaboration/websocket#saved-state). A client shows "saved" only for what is on disk.

A client that catches up receives what the room has stored, never updates still waiting for a missing dependency.

## Catch-up of large documents

Cloudflare limits a WebSocket message to 32 MiB. A frame the room sends that is larger than `EDYTOR_MAX_FRAME_BYTES` (32 MiB by default) goes out as a sequence of chunks, and the provider applies it only once the sequence is complete. Smaller frames are sent whole, so clients without chunk support still sync small documents.

The provider does the same the other way (its `maxFrameBytes` option, 32 MiB by default): an offline backlog larger than one message reaches the room at reconnect as a chunk sequence, which the room reassembles per socket, then admits like any frame (the [frame quota](#quotas) applies to the whole, and a sequence announcing more is refused at its first chunk). With the default quotas no frame the room accepts needs it (the frame quota is below one message); it matters once you raise them. A chunk with no sequence started (the room woke between two chunks and lost the ones it had) closes the socket with `1011` (`chunk sequence lost`): the provider redials and resends.

The room's memory for chunks is bounded:

- A sequence is assembled into one buffer of the size its first chunk announces, allocated then, never into parts copied at the end.
- The sequences in flight on all sockets together take at most `EDYTOR_MAX_BUFFERED_BYTES` (twice the frame quota by default, never less than one frame). A sequence that would pass it closes its socket with `1011` (`room busy`), logged as a `quota` refusal (`quota: 'buffer'`): the room is busy, the sender is not at fault, so its provider redials with backoff and resends. A closed socket releases its buffer.
- A read-only socket's sequence is never buffered: its start is answered with the `read-only` denial, its chunks are dropped, and the socket stays, as for any write it sends.
- A sequence's start counts against the [update rate](#quotas), like a sync message.

`metrics().buffered` reports the sequences in flight and the bytes buffered for them.

## Quotas

Three limits keep one client from filling the object's storage or keeping it busy. Each is a `vars` setting (and an `attachRoom` option), and a socket past one is closed with `4413` (`quota: document`, `quota: rate` or `quota: frame`), its write not applied, logged as a `quota` refusal with `{ user, quota, … }`:

| Variable | Option | Default | Limit |
| --- | --- | --- | --- |
| `EDYTOR_MAX_DOCUMENT_BYTES` | `maxDocumentBytes` | 2,097,152 (2 MiB) | The document's size: what its records hold, uncompressed, plus the updates it holds waiting for a dependency. A frame that would take it past the limit is refused once the room has compacted its update records (they collapse into the live state). A frame that deletes at least as much content as it adds always applies, so a full document can still be trimmed. |
| `EDYTOR_MAX_UPDATES_PER_SECOND` | `maxUpdatesPerSecond` | 50 | Sync messages per second and socket, sustained, with a burst of ten seconds' worth (a reconnect, a paste). The editor sends one per transaction; a script driving the provider should batch its edits into transactions. |
| `EDYTOR_MAX_INBOUND_FRAME_BYTES` | `maxInboundFrameBytes` | 4,194,304 (4 MiB) | One frame a socket sends, reassembled from its chunks; a chunked frame announcing more is refused at its first chunk, before anything is buffered. It must hold a whole document (a client seeding an empty room sends it in one frame): raise it with the document quota. The platform caps one message at 32 MiB. |

The quota closes the socket rather than dropping the frame: the sender's later edits build on the one dropped, so the room would hold them waiting, in memory, for good, and never acknowledge them. It is final rather than redialed, because a redial resends the same edits through the handshake and meets the same quota. The edits stay in the client's document and its local copy, and `saved` stays `false`.

Size the document quota for the room's memory. An isolate has 128 MB, and the live document takes far more memory than it stores. Measured with `bench/room-memory.mjs` (the room's document and its block index, loaded from a compacted snapshot, in Node):

| Document | Stored | Heap | Heap per stored byte |
| --- | --- | --- | --- |
| 10,000 blocks of one short line (24 characters) | 2.2 MB | 101 MB | 46 |
| 2,000 typed paragraphs (60 characters, a transaction a word) | 0.8 MB | 21 MB | 27 |
| 2,000 paragraphs with a bold and an italic run | 1.4 MB | 26 MB | 19 |
| 5,000 paragraphs of prose (400 characters) | 3.0 MB | 51 MB | 18 |

The default of 2 MiB keeps the worst case, a long list of short blocks, near 100 MB. Workers run V8 with pointer compression and Node does not, so a room needs less than these figures: the [soak](#load) read about 20 bytes of heap per stored byte in workerd, through its inspector, for a document 50 writers typed, split and merged (18 in its run near the quota; 27 in Node for typed paragraphs). That is the live heap after a full collection: before one, the soak saw peaks several times higher. A document of long text can take a higher quota: at 20 bytes a byte, 4 MiB is about 84 MB. Leave room for the rest: a compaction and a catch-up each encode the whole document once more, and chunked frames take up to `EDYTOR_MAX_BUFFERED_BYTES`. A room past its memory is reset by the platform and restarts from its rows, so a quota set too high shows as sockets closing and redialing, not as a refusal. Your own server edits ([`transact`](/docs/server/extending#edit-on-the-server)) are not limited.

Inline images count at their size. Without an `upload`, the [image plugin](/docs/plugins/image) (a default plugin) stores each image in the document as a `data:` URL of up to 1 MiB (`MAX_INLINE_IMAGE_BYTES`), so two or three of them reach the default document quota, and the `4413` that follows is final: the provider stops and every later edit stays unsaved. An inline image takes about its own size in memory, not the 18 to 46 times of the table, so for documents that hold images give the image plugin an [`upload`](/docs/plugins/image) that stores the file and answers its URL, or raise `EDYTOR_MAX_DOCUMENT_BYTES` (and the frame quota) by the images' size.

## Hibernation

The room schedules no timers: each entry point runs with `setTimeout` and `setInterval` disabled (the exported `noTimers` helper), because a Durable Object with a pending timer cannot hibernate. Sockets stay connected while the object sleeps; identity comes back from the socket attachments and the document from storage.

## Block roles

Edits the room makes itself ([`transact`](/docs/server/extending#edit-on-the-server)) obey the block roles of the bundled rich-text, code, image and columns plugins (`defaultSemantics`): an edit those roles refuse in a view, such as merging into a divider, moving a code line out of its code block, merging a code block's first line into it or moving a block directly into a columns layout, is refused on the server, and the room shows a [columns layout](/docs/plugins/columns#what-shows) by the same rules as a view.

- **Keyboard policies stay in the view.** What a plugin adds on top (Delete before a code block removes an empty block and does nothing otherwise) belongs to the view: the server applies the plain operation.
- **Other kinds.** Rooms whose clients define other void or island kinds pass their own rules; see [Block roles on the server](/docs/server/extending#block-roles-on-the-server).
- **Client edits are relayed as they come:** the room does not check their roles. To check client edits against your own rules (locks, kinds, sizes), [validate them](/docs/server/extending#validate-edits): the room undoes a frame you deny.

## Settings

Set these as `vars` in `wrangler.jsonc`. All are optional.

| Variable | Default | Description |
| --- | --- | --- |
| `EDYTOR_MAX_ROW_BYTES` | 1,995,904 | Largest stored row. Can only be lowered. |
| `EDYTOR_MAX_FRAME_BYTES` | 33,554,432 (32 MiB) | Largest frame sent whole; larger ones are chunked. Can only be lowered. |
| `EDYTOR_COMPACT_AFTER` | 500 | Update records before the room compacts its rows into one snapshot. |
| `EDYTOR_SAVE_AFTER` | 2000 | ms between the first unsaved change and [`onSave`](/docs/server/extending#save). |
| `EDYTOR_MAX_DOCUMENT_BYTES` | 2,097,152 (2 MiB) | The document [quota](#quotas). Can be raised. |
| `EDYTOR_MAX_UPDATES_PER_SECOND` | 50 | The update rate [quota](#quotas), per socket. Can be raised. |
| `EDYTOR_MAX_INBOUND_FRAME_BYTES` | 4,194,304 (4 MiB) | The frame [quota](#quotas). Can be raised. |
| `EDYTOR_MAX_PRESENCE_BYTES` | 16,384 (16 KiB) | The largest [presence](#identity-and-presence) state a socket may publish, as JSON. |
| `EDYTOR_MAX_PRESENCE_PER_SECOND` | 50 | Presence messages per second and socket, a bucket apart from the update rate ([presence](#identity-and-presence)). |
| `EDYTOR_MAX_BUFFERED_BYTES` | twice the frame quota | The chunk sequences in flight on all sockets together ([catch-up](#catch-up-of-large-documents)). Never below the frame quota. |
| `EDYTOR_LOG` | | `off` silences the room's [log](#metrics-and-log). |
| `EDYTOR_PURGE_AFTER_DAYS` | the retention, else 30 | Days after which deleted content is [purged](/docs/server/history#the-purge); `off` never purges. |
| `EDYTOR_HISTORY_RETENTION_DAYS` | 30 | Days a [version](/docs/server/history) is kept. |
| `EDYTOR_HISTORY_TIME_ZONE` | `UTC` | The IANA time zone of the history's half-day slots. |
| `EDYTOR_LOCKS` | | The data key that [locks](/docs/server/extending#per-block-locks) a block to the user it names, e.g. `lockedBy`. Unset: no locks. |

The rooms blocks [move](/docs/server/moves) to are the `EDYTOR_ROOMS` binding, a Durable Object namespace (usually the room's own). The [history](/docs/server/history)'s store is `EDYTOR_HISTORY`: a KV namespace or an R2 bucket binding, or the variable `"room"` for the room's own storage. Without it, the room keeps no history.

```jsonc wrangler.jsonc
{
  "vars": { "EDYTOR_COMPACT_AFTER": "200" }
}
```

Values that are not positive integers are ignored. Pass your own `Env` type to the class if you extend it: `DocumentRoom<Env>`. With `attachRoom`, pass the same settings as options. To load, save or edit the document from your own code, see [Your own Durable Object](/docs/server/extending).

## Compaction over RPC

`compact()` is also callable over Durable Object RPC, for example from an admin route or your own scheduled job. It returns the number of rows left:

```ts
const { rows } = await env.ROOMS.getByName(documentId).compact();
```

Compaction stores the live document as one snapshot. It collects deleted content the CRDT no longer needs, keeps what it does need (the structure of deleted items, and text a peer's undo may copy back), and never loses an edit: a room restarted from its rows holds exactly the document it held before.

`dropWaitingDeletes()`, also over RPC, drops every [waiting delete](#storage), stored or kept in memory with a waiting attribute change, and returns how many ranges it dropped. Use it when `waiting` refusals show the limit is full. A dropped delete's content shows again if its author returns; an attribute value a waiting change replaces is still replaced if that change applies.

```ts
const { ranges } = await env.ROOMS.getByName(documentId).dropWaitingDeletes();
```

## Diagnostics

`refusals` holds the newest 100 refusals (`MAX_REFUSALS`) of the running instance, each with its `reason` and `detail`; `refusalCounts` counts every refusal by reason. Both live in memory and restart empty; read them inside the object, or return them from an RPC method of your own.

| Reason | What it records | `detail` |
| --- | --- | --- |
| `storage` | A failed append, compaction or registration. | |
| `internal` | An error of the engine or a send. | |
| `waiting` | The deletes of unheld items a frame carried past `MAX_WAITING_DELETES`; the rest of the frame applied. | `{ user, ranges }` |
| `quota` | A write past a [quota](#quotas): the socket closed `4413`, or `1011` for `quota: 'buffer'`. | `{ user, quota, … }` |
| `presence` | A presence entry past the size quota, or the start of a socket's burst of presence messages past the rate: one entry per burst, `refusalCounts.presence` counting each message. The socket stays; see [presence](#identity-and-presence). | `{ user, quota: 'size' \| 'rate', … }` |
| `mark` | Another writer's per-writer block marks a frame wrote or deleted, stripped. | `{ user, writers, ranges }` |
| `forged` | Attribution entries a frame may not write or delete: another replica's `c/<n>` binding, another user's `u/<id>` profile; removed, see [attribution trust](/docs/server/authorization#attribution-trust). | `{ user, keys }` |
| `history` | A [version](/docs/server/history) the room skipped, or a time zone it does not know. | `{ key, bytes, limit }` past its store's value limit, `{ key, error }` when the store failed |

Four more entries are not refusals:

| Entry | What it records | `detail` |
| --- | --- | --- |
| `denied` | A frame [`validate`](/docs/server/extending#validate-edits) denied, undone by the room. | `{ user, touched }` |
| `access` | The room ended or changed a user's access: `expired`, `closed` (`closeUser`), `read`, `write` or `none` (`setAccess`); see [revoking access](/docs/server/authorization#revoking-access). | `{ user, access, sockets }` |
| `orphan` | An unowned id claimed by its dial (after a [restore without a registry](/docs/server/extending#load), or a relay). | |
| `relayed` | Content under an id the room held nothing of, delivered by another replica and kept unowned (see [replicas](/docs/server/authorization#replicas)). | |

## Metrics and log

`metrics()`, also over RPC, returns the room's counters since the instance started (a wake starts them again):

| Field | Content |
| --- | --- |
| `documentBytes` | The document's size as the [document quota](#quotas) measures it: its records, uncompressed. |
| `storedBytes`, `records`, `rows` | What the rows take in storage (a compressed snapshot at its compressed size), the logical records (the generation record included) and their rows. |
| `updateRecords` | Update records since the last compaction (it runs at `EDYTOR_COMPACT_AFTER`). |
| `waitingBytes` | Updates held in memory waiting for a missing dependency. |
| `sockets` | The document's open sockets. |
| `compaction` | Compactions run: `count`, `totalMs`, `maxMs`, `lastMs`, and `lastBytes` (the last snapshot's size). |
| `fold` | Client sync frames folded (admitted, applied, stored, relayed, validated, acknowledged): `count`, `totalMs`, `maxMs`, `lastMs`. |
| `fanOut` | Frames sent to other sockets (`messages`, a chunk counting as one) and their `bytes`. |
| `quotaHits`, `validationDenials` | Writes refused by a [quota](#quotas), frames [`validate`](/docs/server/extending#validate-edits) denied. |
| `refusals` | Every refusal by reason (as `refusalCounts`). |
| `history` | [Versions](/docs/server/history) written and skipped, and the last key written. |
| `purge` | [Purges](/docs/server/history#the-purge) run, the last horizon purged, and what they deleted (`removed`, `emptied`, `marks`, `records`, `candidates`, `claims`). |
| `since` | When the instance started. |

```ts
const metrics = await env.ROOMS.getByName(documentId).metrics();
```

`lastUpdated()`, also over RPC, returns when the room last stored a change (ms since the epoch; `null` for a room that has stored none since it began recording them, with this release), from one row of its `meta` table (`edytor_meta` with `attachRoom`). Clients reach it without opening the document through [`lastUpdated`](/docs/collaboration/persistence#prefetch-and-last-updated), which `routeDocumentSocket` answers.

Times are what the runtime's clock reports. Workers advance the clock only across I/O, so synchronous work such as a compaction often reads `0` ms in production; sizes and counts are exact.

The room also logs one JSON line per compaction (`{ "edytor": "compaction", "ms", "bytes", "records", "rows" }`), quota hit (`{ "edytor": "quota", "user", "quota" }`), denial (`{ "edytor": "denied", "user", "touched" }`), fault (`{ "edytor": "fault", "reason", "detail" }`), version written (`{ "edytor": "history", … }`), restore (`{ "edytor": "restore", … }`), a client whose roles differ from the room's (`{ "edytor": "semantics", "user", "kinds" }`, development builds; see [Block roles on the server](/docs/server/extending#block-roles-on-the-server)) and purge (`{ "edytor": "purge", … }`; see [History and purge](/docs/server/history#metrics-and-log)), with `console.log`, which [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) and `wrangler tail` collect. Set `EDYTOR_LOG` to `off` to silence it, override `protected log(entry)` in a `DocumentRoom` subclass to send entries elsewhere, or pass `log` to `attachRoom` (`false` for none).

## Load

The repository's soak harness (`bench/soak/`) runs many real clients against one room and injects faults while they edit. Each client is a headless document (`createDocument`) on the shipped `WebsocketProvider`. It types at its caret, presses Backspace and Enter, merges, moves blocks, sets marks and data, and cuts text (the mix is `bench/soak/edits.mjs`). It also publishes presence after each edit, and at 20 Hz while it drags a selection (10 % of its time). Clients drop their socket about once a minute (a tenth of those drops are page loads, with a new replica synced from nothing), and go offline for 10 to 60 seconds about twice an hour, still editing, then replay their edits. Every run also forces one offline session and one page load, so even a short run replays and reloads.

Locally the room is the shipped `DocumentRoom` in Miniflare, with the default quotas, the default compaction threshold and its history in its own storage. Faults run on a schedule:

| Fault | How | Every |
| --- | --- | --- |
| Forced compaction | `compact()` over RPC, during traffic | 90 s |
| Hibernation | The instance's memory dropped, sockets kept (`workerd:unsafe` eviction) | 4 min |
| Eviction | The instance dropped with its sockets closed | 6 min |
| Reset | `ctx.abort()`, as on an exceeded limit or a deploy | 7 min |
| Storage outage | Every update append fails, for 2 s (a SQLite trigger) | 5 min |
| Failing compaction | Every compaction fails, for 30 s | 8 min |

The harness measures:

- the ack latency of every edit outside an offline session: from the edit to the room's `messageSaved` that covers it, across reconnects. Edits made while the socket was connected and synced are reported apart from those made while it was down or not yet synced (a dropped socket, or a fault's redial and backoff), which wait for the next connection;
- the replay time of each offline session: from the reconnect to the ack of its last edit;
- the room's `metrics()`;
- the isolate's heap, read through workerd's inspector after a full garbage collection (and, every 10 s, without one), and workerd's resident memory;
- the final document's stored size, against the same JSON seeded fresh and against the document after the room's [purge](/docs/server/history#the-purge) at a horizon of now (`bench/soak/size.mjs`).

At the end every client comes online and settles. Convergence holds when every client's JSON, the room's own `read()` and a fresh joiner's document are equal, and still equal after the room is evicted and loaded from what it stored.

### Results

Measured with 50 clients for 20 minutes, on an Apple M4 Pro laptop shared with other jobs (load average 5 to 55, median 24). Room and clients ran on the same machine. Sizes are in MB of 10^6 bytes (the reports store MiB):

| Measure | Result |
| --- | --- |
| Edits | 22,321 applied, about 18 a second; 6.5 million frames fanned out (1.2 GB) |
| Ack latency, edits made while connected | 21,462 edits: p50 5.6 ms, p90 28 ms, p99 691 ms, p99.9 4.1 s, max 57 s |
| Ack latency, edits made while disconnected | 604 edits (a dropped socket, a fault's redial and backoff; offline sessions apart): p50 880 ms, p99 4.1 s, max 60 s |
| Ack latency, 10 s windows with no fault | Edits made while connected, in the 30 windows that no fault started in the last 40 s of (70 s for a failing compaction): p99 64 ms in the median window, 1.3 s at worst |
| Offline replays | 24 sessions (255 edits): p50 56 ms, max 241 ms |
| Compaction | 48 automatic, p50 18 ms, max 44 ms. 13 forced over RPC, 45 ms p50 and 90 ms max round trip. At 1.8 MB, after a cold load: 75 ms |
| Room heap, live (after a full GC) | 5.9 MB at the start; 36 MB with a 1.80 MB document once the clients were idle: about 20 bytes of heap per stored byte |
| Room heap, before collection | 121 MB at its peak, with 190 MB allocated by V8, right after a storage outage |
| Stored size | 1.77 MB for 400 blocks and 20,778 characters, 72 bytes an edit; the same JSON seeded fresh: 0.16 MB; purged at a horizon of now: 1.67 MB |
| Convergence | 50 of 50 clients, the room, a joiner and the reloaded room equal |
| Restarts | 12 (5 hibernations, 3 evictions, 3 resets, the final eviction), all injected |

Every fault healed without intervention:

- **Hibernation, eviction and reset.** Each one closed or kept the sockets, the providers redialed, and the room loaded again from its rows. The windows after them show p99 8 ms to 1 s.
- **Storage outage.** Each 2 s outage closed every writer `1011`. The providers redialed and resent: the window of each outage shows p99 3.0 to 5.5 s, the next one under 400 ms.
- **Failing compaction.** Edits were stored and acknowledged throughout, and the next compaction after the fault went through.

The slowest edit made while connected (57 s) was made just after the reset at 19 minutes and acknowledged only in the final settle; the slowest made while disconnected took 60 s. The report does not say why they waited (a grown backoff, or a socket the reset left open until the keepalive dropped it), but a writer's edits can stay unsaved for a minute after a fault.

The room did not refuse anything (`quotaHits` 0). Its only refusals were the injected storage faults and one `relayed` note.

A run near the document quota (50 clients at 2 edits a second each for 5 minutes, no faults; 25,056 edits) ended at 1.93 MB with 34 MB of live heap once the clients were idle (about 18 bytes a byte), and 54 MB right after an eviction while all 50 clients caught up again. Ack latency was p50 4.2 ms and p99 153 ms, and the run converged.

**Memory.** The live heap stayed under 70 % of an isolate's 128 MB in both runs, but only the heap after a full collection. Before collection it reached 121 MB (190 MB allocated) after a storage outage in the 20-minute run, and 92 MB (134 MB allocated) in the run near the quota: past 70 %, and, allocated, past the limit itself. Miniflare enforces no memory limit, so whether a deployed room rides out such a peak, which V8 would collect first, is not verified. A room the platform resets restarts from its rows, as the injected resets above did.

Three findings to plan around:

- **Stored size follows edits, not content.** The 20-minute document stores 1.77 MB, about 72 bytes for each edit, while its JSON seeded fresh takes 0.16 MB. That growth is the CRDT structure each edit leaves, and it stays for the life of the document. A document that many people edit all day can reach the default 2 MiB [quota](#quotas) in days, whatever its visible length. Raise `EDYTOR_MAX_DOCUMENT_BYTES` for such documents: the live heap above leaves room. A shorter `EDYTOR_PURGE_AFTER_DAYS` does not help, as it cuts the history and undo for a few percent.
  - It is not deleted content: no deleted item still held its content (the engine keeps only a placeholder), and the room's purge at a horizon of now gave back 5 %, mostly old text delete marks and placement candidates.
  - `bench/soak/size.mjs` replays the mix in memory, 8 replicas and 4,000 edits, and leaves kinds of edit out: about 40 bytes an edit for the whole mix, 20 without Enter and merges, 7 for typing and deleting only, 3 for typing at a caret.
  - In the 20-minute document, of about 103,000 items: each Enter registered a block (its node, incarnation, attribution record and placement candidate) that stays after a merge, as the block it merged into shows its text, so 1,537 blocks are registered for 400 shown, after the purge too; the attribution records list each block's contributors, 40,000 entries; and each edit replaced its block's `lastChangedBy`, leaving the old value's entry, 15,000 of the 21,000 deleted items.
  - The soak's 50 writers and their reloads (148 replica ids) cost about twice the 8 in-memory replicas per edit.
- **Presence fan-out is quadratic.** The room relays each presence message to every socket. With 50 clients all at 20 Hz (`--drag 1`), that is 35,000 frames a second. The room's core ran at 100 % for the whole run, ack latency rose to p50 1 s and p99 19 s, and workerd evicted the busy object once (its sockets carried over). The run still converged. The editor publishes presence on selection changes, at most every 50 ms by default: for rooms with many active editors, raise its `throttle` or narrow what it shares (see [sharing less at scale](/docs/collaboration/presence#sharing-less-at-scale)).
- **A storage outage rebuilds the document per failing frame.** Each frame whose append fails is refused `1011` and the room rebuilds its document from its rows, so an outage costs a rebuild for each writer's frame, the likely source of the heap peak above.

### Run it

```sh
pnpm soak:smoke   # 6 clients, 90 s, every fault on a compressed schedule, one offline session and one page load
pnpm soak         # 50 clients, 20 minutes, the schedule above
node bench/soak/run.mjs --clients 100 --minutes 60 --ops 0.4 --drag 0.1 --faults on
node bench/soak/size.mjs --edits 4000 --without split,merge   # the stored size, in memory
```

`run.mjs` starts the room locally unless it gets `--server`. It writes its report to `bench/results/soak-<time>.json`: the settings, the latency percentiles, a sample every 10 s (room heap, CPU, memory, document size, records, sockets, compactions, refusals), the faults and their answers, the forced offline session and page load, the room's starts, the stored size and the convergence. A run that does not converge also writes every client's state vector and the distinct documents next to it. It exits with code `1` when it does not converge, or when the forced offline session or page load did not happen. The reports of the runs above are `bench/results/soak-wu16-20min.json`, `soak-wu16-near-quota.json` and `soak-wu16-presence-worst.json`, and `soak-size-*.json` for the in-memory sizes. The near-quota and presence reports come from an earlier version of the harness: they keep every edit's latency in one figure, made while connected, and measure no stored size.

### A multi-hour soak on staging

A laptop shares its cores with the clients, so run the long soak against a staging deployment:

1. Deploy the soak Worker to a staging account, never to production: `bench/soak/wrangler.jsonc` deploys `bench/soak/worker.ts`, the shipped room as `SoakRoom`, with routes for metrics, its document, compaction, storage faults and `ctx.abort()`. First set a token. Without it the Worker refuses every request:
   ```sh
   wrangler secret put SOAK_TOKEN -c bench/soak/wrangler.jsonc
   wrangler deploy -c bench/soak/wrangler.jsonc
   ```
2. From one or more machines near the region (100 clients takes about 8 GB for the clients' documents), run:
   ```sh
   node bench/soak/run.mjs --server wss://edytor-soak.<account>.workers.dev/rooms \
     --token <SOAK_TOKEN> --room soak-staging-1 --clients 100 --threads 8 --minutes 360
   ```
   The operator routes get the token in an `Authorization` header. A socket cannot send one, so its URL carries `?token=`, and the token shows in request logs: `wrangler tail` prints it, and Workers Logs, which the configuration leaves off, would store it. Use a fresh token for each soak. Against a deployed room, the hibernation and eviction faults are skipped (they need Miniflare); the reset, both storage faults and forced compaction run. The heap is not readable there: read the room's memory and CPU in the Worker's metrics in the dashboard, and its log with `wrangler tail -c bench/soak/wrangler.jsonc`.
3. Compare the report with the results above. Pass when it converges, nothing restarts but the injected faults, `quotaHits` is 0 unless the document reached its quota, and ack p99 outside fault windows stays under a second.
4. Delete the staging Worker afterwards (`wrangler delete -c bench/soak/wrangler.jsonc`).

## Generation cutover

A container written by the previous schema generation (schema generation 4, the releases before this one back to its bump) converts when the room loads it: its visible document is read as JSON and seeded as this generation's document, which replaces the container in one storage transaction (the room logs `{ "edytor": "convert", "from": 4, "to": 5, "blocks", "bytes" }`, and `origin` is `{ kind: 'converted' }`). Blocks keep their ids, kinds, data, content and marks; undo history, attribution and CRDT identity do not cross, nor what a client of the old generation never sent. Versions in the history written before the cutover read through the same conversion, so `readHistory` and `restoreHistory` still work on them. See [migration](/docs/reference/migration#from-010-next24) for the deploy order.

A container of any other generation is refused; bytes are never converted in place. To move such a document across:

1. Before deploying the new version, make sure `onSave` has mirrored the document as JSON (`value`).
2. Deploy. Rooms of the old generation refuse every socket (`1008`, `refused: container`); `failure` is a `GenerationMismatchError`.
3. Call `reset()` on the room, for example from an admin route. It deletes the document's tables in one transaction and starts again from `onLoad`.
4. Have `onLoad` return the saved JSON. The room seeds it as the new generation's document.

```ts
await env.ROOMS.getByName(documentId).reset();
```

`reset()` throws for any other room: it only replaces a container of another generation.

## Limits

- **A document is capped at 2 MiB stored** by default (`EDYTOR_MAX_DOCUMENT_BYTES`), about 5,000 paragraphs of prose or 9,000 one-line blocks: the room's memory, not its storage, is the limit (see [quotas](#quotas)). One frame is capped at 4 MiB (`EDYTOR_MAX_INBOUND_FRAME_BYTES`), and one message at 32 MiB by the platform; both sides chunk larger frames. The image plugin keeps inline images under 1 MiB: upload larger ones.
- **Document ids** are 1 to 256 characters, not `.` or `..`, with no lone surrogate; user ids are 1 to 256 characters with no lone surrogate.
- **Presence** refills over up to 15 seconds after the room wakes.
- **One document per room.** Rooms do not share state; listing, searching or aggregating documents is up to your application.
- **No auth rules ship with it.** `authorize` is yours; see [Authorization](/docs/server/authorization).
- **A busy document grows with its edits.** Each edit leaves CRDT structure that stays for the life of the document (a block registered for each Enter, attribution, placements, marks, replaced values), so the document quota counts the editing, not only the content: about 72 bytes an edit in the [soak](#load), of which the purge gives back about 5 %. Size the quota for how much a document is edited, not only how long it is.
- **Deleted content goes after 30 days** (`EDYTOR_PURGE_AFTER_DAYS`), from the room and every client; a version or an undo brings it back within them. See [History and purge](/docs/server/history).

For the frame format, or to write a room of your own, see [the protocol](/docs/server/protocol).
