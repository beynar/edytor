## Open units of work

### CW-01 — Concurrent outdent, lift or Turn into on adjacent list items can swap their text order

- **Area:** CRDT correctness
- **Severity:** medium (confirmed)
- **Effort:** M
- **Where:** `src/lib/crdt/edytor-doc.ts:1963` (`splitOut` → `ranksFor`, which is `M.ranksAt` using `Math.random`; see `rand.ts:18`)
- **Failure:** Start from `[p, ul[a, b, c]]`. Ada presses Shift+Tab on `b`, or turns it into another kind. At the same time Bob presses Shift+Tab, Backspace-at-start or Turn into on `a`. Every replica converges to `[p, (empty ul'), b, a, ul[c]]`, so the text reads "b a". Neither serial order can produce that result.
  - It happens on 31 of 240 client-id pairs in each of four gesture pairs, with problems=[] (the replicas converge on the wrong order).
  - It is worse in lists nested directly in a list: b→heading ‖ c→heading gives `cabxd`.
  - It contradicts `docs/editor-delete-contract.md:513-514` and `:540`, and `site/content/docs/collaboration/concurrent-editing.mdx:172`.
  - The pinned rows `rescore7-crdt.test.ts:90` and `:108` pass only because they use the three fixed `CLIENT_IDS` pairs.
  - The mechanism: both lifts draw independent random ranks in the same (left sibling, list) gap.
- **Fix:** Make ranks in the shared gap deterministic:
  - Put a first-item exit (lead-empty outdent, `mergeBackward`, or `liftOut` of a first item) at the low end of the gap, just after the left sibling.
  - Put `splitOut`'s new head list and the moved middle items at the high end, just before the source list.
  - A deterministic tie-break keyed to the source list's rank is an alternative.

  Add a `converge` sweep over many client-id pairs to the rescore7 rows and to the wave10-liftout concurrency rows, and assert `allText` order. If you choose not to fix it, rewrite contract:513-514, :540 and concurrent-editing.mdx:172 to say order is not guaranteed, record it as a residual, and correct the "keeps text order in every case" claim in `docs/reviews/2026-09-30-rescore-7.md:7`/`:218`.

- **Repro:** `scratchpad/rescore9/order-swap-repro.test.ts`
- **Done when:** All four gesture pairs, plus the nested-list heading case, give `pabc` (or the nested equivalent) on every one of at least 240 client-id pairs. The swept rows are in the CRDT lane and green. Either the docs' order promise holds, or it has been withdrawn in every place listed above.

### CW-02 — Code-line Tab or Shift+Tab over several lines writes a partial indent when one line is vetoed

- **Area:** Code organization, API ease of use
- **Severity:** low (confirmed in both areas)
- **Effort:** S
- **Where:** `src/lib/plugins/code/CodePlugin.svelte:53` (the `indent()` loop inside one `dispatcher.run`)
- **Failure:** A plugin runs `onBeforeOperation: ({block, prevent}) => block?.data?.locked && prevent()`. The code block holds `['one', 'two'{locked}, 'three']`, the selection runs from l1 to l3, and the user presses Tab. The result is `['\tone', 'two', 'three']`: line 3 is skipped even though nothing vetoed it, and `dispatcher.last` is `{insertText, applied}`. Shift+Tab behaves the same way. This matches neither rule in `operations.mdx:71-73` (the whole command refused, or a per-part refusal). One undo restores the lines.
- **Fix:** Loop with `edytor.dispatcher.each(step > 0 ? 'indentLines' : 'dedentLines', touchedLines() ?? [], line => …)`, and record caret `shifts` only for lines that applied. Alternatively, dispatch one composed plan for the whole gesture. Add code-line Tab to the per-part list in `operations.mdx:73`.
- **Done when:** A DOM row with a locked middle line shows l1 and l3 indented and l2 unchanged, with the status `applied`. The mirror row passes for Shift+Tab. operations.mdx lists the gesture.

### CW-03 — `Block.isEmpty` and `hasContent` changed meaning without a migration note

- **Area:** Editing behaviors, Documentation
- **Severity:** low (confirmed in both areas)
- **Effort:** S
- **Where:** `src/lib/block/block.svelte.ts:237`; `site/content/docs/reference/migration.mdx:143`
- **Failure:** Both getters now count inline atoms, so a block that holds only a mention is no longer "empty". 0.0.11, 0.1.0-next.0 and 0.1.0-next.1 all shipped the text-only rule. A plugin that relies on `block.isEmpty`, as `example-plugin.mdx:86` does, changes behavior after upgrading. migration.mdx says it lists "every public change since 0.0.11" but has no entry for this.
- **Fix:** Add a bullet to migration.mdx and to the next pre-release notes: "`block.isEmpty` / `block.hasContent` count inline atoms: a block holding only a mention is not empty. To test for text only, use `block.content.every(p => !(p instanceof Text) || p.isEmpty)`." Optionally, list both getters in the Block row of `concepts/editor-instance.mdx:89`. A docs-drift row can pin it.
- **Done when:** migration.mdx has the bullet, and docs-drift stays green.

### CW-04 — `onDeleteSelectedBlocks` does not run when typing, Enter or paste replaces a block selection

- **Area:** API ease of use (refuted under Code organization; see Refuted)
- **Severity:** low (confirmed as a DX gap)
- **Effort:** S
- **Where:** `src/lib/selection/replaceSelection.ts:205-216` (`replaceSelectedBlocksWithEmptyBlock`); `src/lib/clipboard/insertClipboardFragment.ts:46`
- **Failure:** A plugin runs `onDeleteSelectedBlocks: ({prevent}) => prevent()`, and blocks a and b of `[p a, p b, p c]` are block-selected. Backspace, cut and the menu's Delete keep both blocks. Typing `x` leaves `[p 'x', p c]`, a paste of `zz` leaves `[p 'zz', p c]`, and Enter replaces both blocks. The docs' trigger list is exact (`plugins.ts:148`, `writing-plugins.mdx:193`). Two things overclaim: the code comment "guards them all" (`:172`) and the test `describe` title "Every block-selection delete runs onDeleteSelectedBlocks (DR-code-2)" (`wave11-kinds.test.tsx:449`).
- **Fix:** Pick one of two:
  - (a) Run the same `dispatcher.intercept` in `replaceSelectedBlocksWithEmptyBlock` and in the paste and drop replace paths, and refuse the insertion when a plugin prevents it.
  - (b) Rename the describe block, and add one sentence to `writing-plugins.mdx:193`: typing, paste and Enter over a block selection replace the blocks without running the hook, and `onBeforeOperation` with `effect.removes` is the guard for those paths.
- **Done when:** Either a DOM row shows typing, Enter and paste refused by the hook, or the describe title and comment are accurate and writing-plugins.mdx states the scope and points to the `effect.removes` guard.

### CW-05 — Every divider triggers a Svelte `dynamic_void_element_content` dev warning

- **Area:** API ease of use
- **Severity:** low (confirmed)
- **Effort:** S
- **Where:** `src/lib/components/Block.svelte:103`
- **Failure:** `<svelte:element this={element.tag}>` always has a body, so for `hr` the compiler emits `validate_void_dynamic_element`. Each divider mount logs one warning in dev and in the DOM tests. Consumers see library noise they cannot fix. The model and the rendering are correct, and production builds strip the check.
- **Fix:** Render void tags through their own bodiless `{#if VOID_TAGS.has(element.tag)}<svelte:element … />{:else}…{/if}` branch. Keep every attribute and `use:register` on it.
- **Done when:** A DOM row renders two dividers with no `console.warn` calls.

## Refuted

- **`onDeleteSelectedBlocks` bypassed by typing, Enter or paste (Code organization, filed low): refuted in this area.** The behavior is real, but no user-facing contract claims the hook covers those gestures. `plugins.ts:148`, `writing-plugins.mdx:193` and `block-menu.mdx:89` list exactly Backspace, Delete, a cut and the block menu's Delete. On master the hook only ever ran from the Backspace/Delete path, so wave 11 widened coverage and removed none. The docs point to `onBeforeOperation` with `effect.removes` (`operations.mdx:75-89`, `lockedBlocks`) to protect blocks, and the `insertFlow` replace plan exposes the removals to that guard. The only overclaim is an internal test `describe` title. It is not counted under Code organization. The API verifier confirmed the same behavior as a low DX gap, so it stays open there as CW-04.
- **CRDT reviewer's possible +0.2 (bug older than wave 11): not taken.** The reviewer declined it: the order swap breaks the promise that the re-score 8 verifier relied on to refute the concurrent-undo swap.
