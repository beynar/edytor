# Plugins and chrome

What a plugin contributes, the bundled plugins and their defaults, labels, block handles and the block menu, and the chrome the overlay draws beside the host (`src/lib/plugins.ts`, `src/lib/plugins/`, `surface/overlay.ts`).

## Plugins

`Plugin = (editor) => definitions & operations` (`src/lib/plugins.ts`). A plugin contributes:

- kind records (`blocks`): `snippet`, `element` and `contentElement` (a tag, `{tag, attributes}`, or `(data, id) => …`), `viewState`, `void`, `island`, `lines`, `layout`, `rendersContent`, `defaultChild`, `continues` (list-like Enter), `container` (a header over its children: toggle, callout, quote), `presets` (slash menu, markdown, "turn into"), `empty`, `html`/`plain` export, `parse` (HTML import), `transformText`, `normalizeContent`/`normalizeChildren`, focus/select hooks;
- mark records (`marks`): `tag` + `attributes(value)` (the one element the core renders and the clipboard exports), an optional `snippet` (custom markup inside a core span), `parse` (HTML import), `void`, `edge` (`inclusive | exclusive | side-dependent`), `copy` (`false`: copy and cut leave it out, `createEdytorClipboardFragment`; the comment anchor's), `toolbar` (`run`: the button calls it instead of toggling); atom records (`inlineBlocks`): `snippet`, `plain`, `html` (clipboard HTML) and `parse` (HTML import claims an element inside a line as the atom);
- input rules (`{ find, replace(match, ctx) }`: text typed at the caret, a string or the rule's own writes through `ctx.remove(then)`, block offsets; no rule in a code block's lines) and `triggers` (`{ char, items(query), onPick }`: a menu at the caret, its `menu` snippet in the overlay, keys through the plugin's `hotkeys` before its own; `onPick`'s first operation takes the trigger's removal as its lead; rows are keyed and named by position, so two may share a label; Enter during a pending search picks the answer's first row, never an older query's), both wired into the hooks of the plugin that returns `withRulesAndTriggers(edytor, definitions, { inputRules, triggers })` (`plugins/triggers/triggers.ts`; the composition root wires none, so a view whose plugins declare none ships no trigger menu); never parse typed text in a plugin's `onBeforeOperation` for these;
- `hotkeys` (typed `HotKeyCombination`: up to three modifiers in any order; unknown tokens fail types and warn in DEV), `commands`, and hooks (`onBeforeOperation`, `onAfterOperation`, `onBeforeInput`, `onCopy`/`onCut`/`onPaste`, `onDeleteSelectedBlocks`, attach hooks that may return a cleanup, `placeholder`).

- Every bundled plugin is one factory, `createXPlugin(options?)`, with no constant beside it (the two without options too: `createArrowMovePlugin()`, `createMarkdownShortcutsPlugin()`).
- Duplicate definitions and commands: **first wins**, a definition field by field (`define` in `edytor.svelte.ts`: a field the first leaves out is the next one's, so an app's plugin naming only a kind's `snippet`, listed first, restyles it and keeps its roles, presets and hooks; the one way to restyle a kind, no `<Edytor>` snippet props); a command whole.
- Extensions read the document through handles and view objects, never Yjs types.
- Bundled and exported:
  - rich text (with toggle headings, `toggle-heading`: a `details` whose `summary` holds the `h1`–`h3`, a container as the toggle, presets Toggle heading 1–3 reached from a heading by `> ` and from a toggle by `#`–`###` through `KindPreset.markdownFrom`; with the link UX, `link.*`: a URL typed before a space or pasted at a caret is linked as an undo step of its own after the text, `typedLink`/`linkText` in `richTextOperations.ts`; Mod+click opens a link, `openLink`; container bodies, `body.*`: an open toggle's or a callout's empty body shows a hint, `EmptyBody.svelte`, `data-edytor-empty-body`, chrome inside the kind's markup whose click is ONE command, `openBody`, and over which a handle drop goes `inside` (`overEmptyBody`); a childless block this view retypes into a toggle opens, from `onBeforeOperation`/`onAfterOperation` through `onBlockAttached`; a callout is an icon, a title (its own text, semibold) and a content (its children, `body: true`, so Enter at the title's end goes into it, `bodyShows`); its icon, `callout.icon`, is `data.icon`, the view's default from `createRichTextPlugin({ callout: { icon } })` when unset (`callouts.ts`: `iconOf`, the per-view `calloutIcons` and `calloutPickers`), none when `''`, picked in the overlay by the view's one `CalloutIconPicker`, its own plugin `createCalloutIconsPlugin({ picker, icons })` (`calloutIcons.svelte.ts`: `set`/`remove`, the `keys`/`popup` attachments and `option(i)` rows that an app's `picker` snippet uses, placed by the app under its `anchor`; rich text's callout `menu` offers the block menu's `callout.icon` row while the view lists a picker, the keyboard's way in; a view without it ships no picker); its HTML is `<div data-edytor-callout="💡">`, read back by its `parse` hook)

- **The chrome is headless.** The package draws no menu, popup, block handle, panel or card: every surface renders the app's snippet through one host, `mountChrome` (`plugins/chrome.ts`, `Chrome.svelte`: shown while its controller says so, closed when the view turns readonly), or a placement host of its own where the surface needs one (`BlockHandles.svelte`, `TableChrome.svelte`, `CommentsSidebar.svelte`, `SuggestionBars.svelte`, the code header and language panel, the equation panel, the callout picker, the image chrome's toolbar slot, the empty image and media hosts). Without its snippet a surface renders nothing (nothing is mounted) and its controller still works (`headless-chrome.test.tsx`). One surface, one snippet: no row snippet beside a whole-surface one, no default branch beside the snippet.
- **The ready-made chrome** is the Notion-style markup (2025 light theme), in shadcn-svelte components on the app's shadcn tokens, released as the `edytor-chrome` item of the shadcn-svelte registry (`registry/edytor/chrome/`, outside the package: it imports `edytor` by name and the shadcn components as `$registry/ui/…`; nothing of `src/lib` imports it; `tokens.css` maps `--notion-*`/`--edytor-*` onto `--background`, `--popover`, `--muted`, `--accent`, `--border`, `--ring`… and gives the block and syntax colours a `.dark` palette). A controller's popup stays its controller's: its markup is shadcn's `Button`, `Input`, `Kbd`, `Separator`, `Avatar`, `Textarea` and classes (`ui.ts`: `row`, `surface`), never bits-ui's Command or Popover state, which would be a second owner of the popup's focus, keys, ARIA and position; a surface rendered once per block (the code header) uses `buttonVariants` classes on a native button, no component boundary (`render-markers`) (`chrome.svelte` exports one snippet per surface from its `<script module>`, each rendering a component of that folder, which holds the markup and its styles, since a module's own snippets carry no styles in a build; `plugins.ts` passes them to each factory: `slashMenuPlugin`, `blockMenu(options)`, `blockHandlesPlugin`, `createCodePlugin()`, `table(options)`, `image(options)`, `mediaEmptyPlugin` (every empty image and media panel), `calloutIconsPlugin` (the callout picker), `mention`/`pageLink`, `comments`, …). The demo route, the `/test/*` routes and the DOM tests list these (the tests import them under the factories' names, `image as createImagePlugin`; `EdytorHarness` adds `blockHandlesPlugin` unless `blockHandles: false`), so every browser spec and DOM row runs the same markup. The docs' examples are the short versions. The matching document stylesheet is `src/lib/themes/notion.css`, shipped as `edytor/themes/notion.css` and scoped under `.edytor-notion` (the document only: the empty image and media states are the demo's). **Every look is the theme's**: a plugin's own CSS (`code.css`, `table.css`, `columns.css`, a component's `<style>`) keeps only what makes its blocks work (layout: columns, a table's grid, an image's alignment; scrolling: code, a wide equation, a table; an embed's frame size, a player's width; what is never selected: a code header, an empty body's hint; an atom on one line) and where the overlay's cues stand and when they show (position, size, z-index, pointer-events and visibility states, the states as data attributes: `data-shown`, `data-dragging`, `data-blocked`). **The overlay's visual cues are the theme's to paint**: the block drop line and nest backdrop, a table's drop line and resize line, a column band's guides, the image's resize pills and other users' carets, ranges and name pills (each peer's colour an inline `--edytor-remote-color` on its caret and ranges, never a baked background) are painted by `notion.css` under `:is(.edytor-notion, .edytor-notion + [data-edytor-overlay])` (the overlay is the host's next sibling, so the class may be on the editor itself); without the theme they are unpainted (`tests/editor-dom/theme-cues.spec.ts`). Padding, colours, hover, borders, fonts, a button's reset go in the theme (`.edytor-notion …`, keeping each rule's specificity under the theme's `a` rule where a look was the link's), and the site's `customization/styling#without-the-theme` lists what an app without it gets.
- The demo route (`src/routes/+page.svelte`) and the site's live editor use that theme, `richTextPlaceholder` and the shipped plugins with the demo's chrome, including the block menu (the demo route builds it with `blockMenu({ linkTo })`) and the columns plugin, listed explicitly (it is not a default; the demo route also lists `findPlugin`, `/test/dom` with `find=true`, and the marquee, `marquee({ container: '.demo-main' })`, `/test/dom` with `marquee=1`), each with a two-column example in its value.

Default plugins: `<Edytor>` (`withDefaults` in `components/Edytor.svelte`) adds `createArrowMovePlugin()`, `createSuggestionsPlugin()` (its keys; no bar without a `bar`), `createImagePlugin()` (its kind; no chrome) and `createRichTextPlugin()` after the app's `plugins` (its kinds and keys win), each unless the list already has one of its kind (any instance of that factory counts: `branded`/`brandOf` in `plugins/brand.ts`, one registry); `defaultPlugins={false}` opts out. `createColumnsPlugin()` (like code, find, page, toc, table, the media plugins, the block handles, the menus, the toolbar and markdown shortcuts) is never added: apps list it, in every view that opens layouts (a view without it renders them as unknown kinds), while `defaultSemantics` holds its roles for the room and headless documents. - Change the rule there and in that table, nowhere else.
- The slash menu opens only at a text start or after whitespace and matches each query word, in order, as a word prefix of a label or keyword (`matchesQuery` in `kinds.ts`, shared with the block menu's search, so `/to do` stays open); a replacing kind (`empty`) converts in place only a block holding nothing but the query (`holdsNothing` reads `dispatcher.pendingLead`), else it is inserted after the block.
- Emptiness is one rule: `block.isEmpty` (and `holdsNothing`) count inline atoms, so a block holding only a mention is never treated as empty (a public change, listed in `reference/migration.mdx` under the upgrade from the previous pre-release).
- Enter or Shift+Enter over a block selection removes nothing: it leaves the selection for the caret at the end of the first selected block's line, as Escape does (`selectedBlocksLine` in `selection/replaceSelection.ts`, Notion; Escape over voids alone goes to the next shown line, else the one before, through `selectedBlocksExit`, never into a divider's phantom text); Mod+Enter only opens/closes toggles and checks to-dos (Notion), each shown block it is in (`shownSelectionBlocks`, `flipToggles`), never splits.

**One way to write a piece** (both tiers, site `customization/menus#the-pattern`): a payload's attachments (`{@attach x}`) give an element what the editor needs of it (id, role, the ARIA it keeps in step, keys, presses, marker); every other field is a value the markup renders or a function it calls; nothing is spread, no `use:` action, no handler prop to pass. An attachment's attributes are invisible to Svelte's scoped CSS and to a server render, so a row's look is the markup's (`data-selected={item.selected}`), never an attribute the attachment writes. A row's id is set by its attachment after the elements before it ran their effects: `inPage` (`plugins/list.svelte.ts`) reads `named`, which `optionAttachment` bumps, so the field naming the highlighted row looks again.

## Block handles and the block menu

- Each handle is a `+` (dispatches `BLOCK_ADD_EVENT`; the slash menu answers it and adds nothing until a row is picked — typing goes to the menu's query through the element the snippet gives `keys`, and Escape, a press outside, focus leaving or readonly close it with the selection given back — then `BlockAddition.insert` adds the parent's default kind below, Alt above, and runs the command in ONE transaction and undo step; a command that answers `false` or is refused with nothing applied is taken back inside that transaction, which the history then does not capture (undo and redo stacks untouched, selection given back); an empty default-kind block is converted instead; unanswered, the `+` inserts the empty block at once. The `+` menu lists only commands whose `isEnabled` holds for the block being added (`additionView` in `SlashMenuController`: a view whose caret is in a stand-in of that block), so commands read the selection from their argument; its field is its one keyboard owner (rows are no Tab stops); a `+` clicked over a grip's menu first gives back the pre-grip selection (`BlockHandleController.#ungrip`)) and the ⋮⋮ grip.
  - A grip click selects the block (an atomic block selection; a block selection already holding it stays, and the block menu then acts on all of it; over a text range across blocks, the blocks it covers), then dispatches `edytor-block-activate` (`BLOCK_ACTIVATE_EVENT`, `{ block, anchor }`, cancelable) on the editor node.
  - `blockMenuPlugin` listens for that event and answers it with `preventDefault()` to keep the keyboard; unanswered, the controller focuses the editor so the keys act on the selected block; an app's own listener answers it the same way (one path: no callback option).
  - Layouts and columns have no handle; a block in a column has its `+` (Alt+click: a new column right of its column, `move` `right`) and grip in the gap, right of the resize band (`gaps.ts`).
- The block stays selected while the block menu is open. Its actions return a text caret with `selection.setCaret({ block, offset })` (inside the editor, `selection.selectText(text, offset)`), which replaces the atomic selection, then focus the editor. A DOM range alone cannot replace an atomic selection.
- Moves go through `edytor.canMove`/`edytor.move` everywhere (drag and drop, handle keys, arrow move, the block menu).
  - A handle's drag, Alt+arrows and click take the selection's blocks through one resolver, `BlockHandleController.dragBlocks` (the outermost of `movable(...)` over a block selection's blocks as clicked — never `selectedMembers`, so a selected list's item drags alone — or a text range's `getSelectionBlocks`, when the handle's block is among them, else that block alone; Mod+Shift+↑/↓ over a text range takes the same blocks, and over a block selection its `outermost`; after a move `selectMoved` keeps the moved blocks' selected descendants selected — only when the block selection held the whole group, else the moved blocks alone, the drag's rule; a handle's Alt+arrow over a text range covering its block keeps the range, as Mod+Shift+↑/↓ does; a drag's undo step restores the selection held before its start, `history.began`); a drag's placement is sticky across gaps, and below the document's last block all the way down (the pointer's x still picking the level; out of the editor's width it clears), never over another block's own row — a drop target sticks while it or a target inside it holds the placement, since PDD keeps an inner target only while every outer one of its chain sticks, and a left target hands the placement to the innermost one still current (`onDragLeave`); a drag fixes that group at its start, marks its count as `data-count` (no badge), and drops it as ONE `move` call (any parents; a refused group moves nothing).
  - The dispatcher opens a closed toggle the blocks of a move land in or that adopts blocks (`reveal`, after every `moveBlocks`, `nestBlock`, `unNestBlock(s)` it writes); callers do not wrap it.
  - An `in`/`out` step over siblings moves each run of adjacent ones on its own (`dispatcher.each`), as Tab does, so it never reorders the text.
  - A move refused before any command runs (readonly, `canMove` false) still sets `dispatcher.last` to `refused`; inside one `dispatcher.run`, a step that applied is never overwritten by a later refused or no-op step.
- List containers (`rendersContent: false`, not void/island — `block.isContainer`) are never converted (`convertible` is false; `convertedBlocks` in kinds.ts skips them, so the items selected with them convert) and never count as touched by a text range that starts or ends in them (`getSelectionBlocks` skips those, so Tab/Shift+Tab over a range move the same blocks as the rows block-selected; a list the range runs through stays in, so it moves in order with its neighbours, and `moveRoots` groups them by parent while `edytor.move` (`parts` in moves.ts) moves each run of adjacent siblings on its own, so no key reorders text).
  - Turn into and the horizontal rule place the new kind through one helper, `placing` in kinds.ts, prepared from the payload hooks leave (a rewritten kind is placed for that kind, its `normalizeContent` runs on it, and the caret follows it; `dispatchPlan`'s `then`): `facade.prepare.liftOut` lifts the item out of every list it does not fit (`facade.landingOf`; a divider or code block inserted after an item: the list splits after it), composed with the retype as ONE plan (never a loop of dispatched lifts: a veto must keep everything); a block's own kind (a data-only change) never lifts it.
  - `liftOut` and `unNestBlocks` split a list with one routine, `splitOut`.
  - What a split, a first-item lift, an outdent or a merge moves out of a block, and the blocks `splitBlock`/`insertFlow` at a position create, is placed by where it came from, never by who moved it: a new slot goes right after its left neighbour's unit, a move record stands in the gap with a side (after-records before before-records), and two records at one origin sort by their blocks' order in the sequence they leave (fork patch YP22, `sourceOrder`): two peers' concurrent splits keep the text order whatever their client ids, one gesture each between syncs (residuals in the delete contract).
  - The pieces of one text that stand where they were made read in the text's order on every client-id pair by construction (`order.split.text`): a split-born block's slot carries the text after its split point, and the engine sorts the slots of one origin by it (fork patch YP22); a paste's lines at the split carry the same key, so they stay with its tail.
  - Only those paths rank by source: inserts beside a block (Enter at a block's start or end, Duplicate, +; a container header's Enter, whose tail becomes a plain first child; a `whole` or `replace` `insertFlow`: a block-selection paste, a paste or typing over selected blocks) take a plain rank, or, right after a block this client ranked, extend its run there (`order.insert.run`: `ranksFor(…, run)`, the data arrays' `rankAfter`, so one peer's consecutive lines never interleave with another's), several gestures by one peer before sync (Turn into over several blocks is one plan per block, Shift+Tab one per run of adjacent blocks) and moves (drag, handle Alt+↑/↓/→, Mod+Shift+↑/↓, block-menu Move, Tab) take plain ranks and are not claimed (`order-scope.test.ts` pins them; do not widen source ranking without passing `rank-growth.test.ts`).
  - A source rank's first part segment is followed by one tied by the client's clock, so one client never mints one twice in a gap and a later gesture's blocks never interleave an earlier one's; `rankBetween` stops descending once its prefix is below the right bound.
  - A command over several parts (Turn into over several blocks, Tab over several runs, code-line Tab/Shift+Tab over several lines, formatting across blocks, Duplicate) runs through `dispatcher.each`: a refused or vetoed part is skipped and the others apply; a block-selection delete (keyboard — every Backspace/Delete chord, word and line deletes too: `wordAndLineDeletes` in bindings.ts at keydown, and `runBeforeInputDeleteCommand` for any delete intent's `beforeinput` — cut or block menu) goes through `deleteSelectedBlocks`, which runs `onDeleteSelectedBlocks` and then one `deleteBlocks` plan.
  - Every path that removes a block selection asks `keepsSelectedBlocks` (replaceSelection.ts) first — that delete, typing and composition (`replaceSelectedBlocksWithEmptyBlock`) and paste (`pasteFlow`); Enter and Shift+Enter remove nothing (`selectedBlocksLine`) and never ask — and a kept selection refuses the gesture (`dispatcher.last` = `refused`).
  - A composition over a block selection replaces it at `compositionstart` (`Composition.#rangeless`, over a selected atom and a text range across blocks too: the new block is rendered with `flushSync` and the DOM caret parked in it by `projector.park` before the IME writes, as a block selection shows no DOM range and the IME would write at the editable's start); refused, the IME writes into `selectedBlocksExit`'s line, which the tail restores.
  - `#release` clears the re-placement baseline (`#where`/`#order`), so that replacement's commit never ends the new session.
  - Enter in an empty item leaves the list through `unNestBlock`.
  - Enter keys off `block.list`, so an item outdented into its outer item keeps outdenting; a container's `itemKind` (`numbered-list-item` for `ordered-list`) is the kind its items show as, so converting to it is a no-op and `rowOf` names items by it.

- **Resize drags** (the image's handles, a table column's band, a layout gap's band) are one gesture, `BandDrag` (`plugins/bands.svelte.ts`) over one tracker, `trackDrag` (`dnd/track.ts`): the press captured (a pointer on the document, a lone `mousedown` on the window), each move the controller's view-only preview, the release its one write and the editor's keys; Escape, a cancel or a view that no longer permits writes end it with nothing written.
- **Accessibility** (site `editor/accessibility`): the root is the `textbox`, named by the view's `aria-label`/`aria-labelledby`/`aria-describedby`/`id` props (`Edytor.svelte`). A popup's ARIA has one writer: the markup rendering it publishes `{ id, haspopup?, active?, keys?, opener? }` to `edytor.popups` once it is in the page, through its controller's `popup` attachment (default and custom markup alike); the root renders the newest, a handle's `+`/grip reads `openedBy` for `aria-expanded` (the textbox takes none, WAI-ARIA 1.2). The keyboard's owner names the highlighted row: the root for a typed `/`, the menu's own field for the `+` (a `combobox`) and the block menu. The toolbar is reached with Alt+F10 (roving tab stop; Escape is `controller.release`), every key in it stopped from the editor. A column band is a focusable `separator` (`resize.key`, one `transact` per press; the caret's layout shows its bands). `edytor.announcer` is the polite live region (`[data-edytor-live]`, overlay). A block's `dir` is `blockDir` of its own text (first strong character, none: inherit), owned by the attribute table: on the block, never the text element (engines move the caret by the paragraph's direction). The list kinds' `li`/`ul`/`ol` are `role="none"` (items are sibling blocks). Chrome text grays are `#73726e` (AA). `tests/editor-dom/a11y.spec.ts` is the axe audit (WCAG 2.2 A/AA; `target-size` a known gap: the 18px grip), `tests/editor-dom/bidi.spec.ts` the bidi rows.
- **Suggestions** (`edytor.suggestions`, `session/suggestions.svelte.ts`; site `editor/suggestions`): a view's proposed content at a position (`after`/`before`/`inside`/`end`/`replace`, by block id or a range's anchors), session state only: never in the document, history, presence or another view until `accept()`, one dispatcher command (`acceptSuggestion`, CUT `both`) placing it as a paste does (`prepare.insertFlow` at `{slot}`/`{replace}`/the text's end, `flow.place`; a text range: `replaceRange` then the flow at its caret). It survives selection changes and is dropped (`prune`, from the commit) when its block dies. A block suggestion renders in the host as one view-only group (`components/Suggestion.svelte`: `[data-edytor-suggestion]`, `contenteditable=false`, the kinds' own rendering through `Block`'s `preview` cells, no handle, no ids, no text elements), registered with the observer as `preview` (never compared or healed) and skipped by the truth oracle, selection mapping (`SUGGESTION` in `selection.utils.ts`), chrome presses and the drag clone; an `end` suggestion is the ghost text (`[data-edytor-text-suggestion]`); replaced blocks carry the owned `data-edytor-suggestion-replaced`, a replaced range is overlay rectangles (`components/Ranges.svelte`, the one layer of marked text runs: the find matches and a comment's draft too, `runOf` a run in block offsets). The keys are `createSuggestionsPlugin()` (a default), the bar `createSuggestionBarPlugin({ bar })`.
- **Shared suggestions** (the same list, `suggestion.shared`; `sugg.*`): in the document (`facade.suggest`), so every replica, the room and a reload see them with their author (`by`, `via: 'ai'`). A view suggests while `edytor.suggestions.suggesting` (forced on while `document.access` is `suggest`): `Dispatcher.write` hands each plan to `suggestions.written`, which continues the open suggestion while the plan touches the block it last wrote in or a neighbour, opens another elsewhere, and announces what the document's `apply` refuses (a move, a merge, a retype, a data change or a format: `labels.editor.notSuggested`; `canMove` is false too). Decisions are one command each, `acceptSuggestion`/`rejectSuggestion` (payload `{ changes }`, CUT `both`), whose writes are id lists and the view's own block operations; only a view that may write and whose `document.access` is `write` decides (`canDecide`); the author's `discard` rejects, by a writer of theirs when the view may not decide. An app's `add(at, content, { shared: true })` writes live as it streams (`write`: what it wrote before removed for real, the answer so far inserted again), its own writer, outside the history. Rendering: the overlay's one `Ranges` layer `suggestion-range`, whose rectangles name themselves (`suggestion-inserted`, `suggestion-deleted`, the author's colour in `--edytor-range-color`), the block attribute `data-edytor-suggested` (`inserted`, `split`, `removed`); the bar plugin places a shared suggestion's bar under its last changed block, its payload gains `reject`, `canDecide` and `author`.
- Where a drop lands is one resolution, `DropResolver` (`dnd/placement.ts`: the rows, the halves, the levels, the margins, the beside bands), for a drag described as `Drag` (the blocks it moves and the placements the document takes for it). The block handles' drag (`BlockHandleController`) wires it to the drag library (its drop targets, stickiness, `placement`); files dragged from outside (`plugins/fileDrop.ts`, `drop.files.place`, installed with the view's `FileUploads` by the first media plugin given an `upload`; the host is a drop target of Pragmatic's external adapter, `dnd/external.ts`, loaded only by those plugins; the core's `events/onDrop.ts` takes the placement the target resolved at the drop through the port `ViewUploads.drop.take()` (the adapter's window listeners capture, so its `onDrop` runs first), and without uploads swallows a drop carrying files; during the drag the kinds are the ones the uploads would place the dragged items' MIME types as (a vendored change exposes them, `UPSTREAM.md` change 4), every kind the uploads take where the engine hides the types) read it from the adapter's `onDragEnter`/`onDrag` (`hitAt`, `over`, `margin`), with no block moving and the places `canPlaceNew` takes, with or without the block handles plugin. `DropIndicator` (`dnd/dropIndicator.ts`) draws it for both (the bar, the nest backdrop, in the overlay, measured per frame; its structural CSS is `components/Edytor.svelte`'s); `dnd/geometry.ts` holds what they read (a placement's shape, a block's own row and first text line, one nesting step, the drop reach's zones), `dnd/stacking.ts` when a layout stacks. Never add a second placement rule or indicator for a new kind of drag: give it a `Drag`.
