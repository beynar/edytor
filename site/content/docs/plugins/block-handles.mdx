Block handles are the two buttons left of each block, as in Notion: a `+` that adds a block, then the ⋮⋮ grip. Drag the grip to reorder, nest or outdent a block, or every block the selection covers; focus it and use <kbd>Alt</kbd> with the arrow keys to move it; click it to select the block and open a block menu, such as the bundled [block menu](/docs/plugins/block-menu). `<Edytor>` includes them by default.

## Enabling and configuring

The `blockHandles` prop of `<Edytor>` controls the plugin:

```svelte
<script lang="ts">
	import { Edytor, type BlockHandleActivation } from 'edytor';

	const openMenu = ({ block, anchor }: BlockHandleActivation) => {
		console.log('open a menu for', block.id, 'next to', anchor);
	};
</script>

<!-- Default: handles with drag and drop. -->
<Edytor />

<!-- No handles at all. -->
<Edytor blockHandles={false} />

<!-- Handles and keyboard moves, no pointer drag, and a click callback. -->
<Edytor blockHandles={{ draggable: false, onActivate: openMenu }} />
```

<TypeTable
  type={{
    blockHandles: {
      type: "boolean | BlockHandlesOptions",
      default: "true",
      description: "false omits the handles. An object configures them.",
    },
    draggable: {
      type: "boolean",
      default: "true",
      description: "false keeps the handle and its keyboard moves, but disables pointer dragging and drop targets.",
    },
    onActivate: {
      type: "({ block, anchor }: BlockHandleActivation) => void",
      description: "Called when a grip is clicked, after the block is selected (a block selection that already holds it stays; over a text range across blocks, the blocks it covers are selected). anchor is the grip element, to position a menu against. Without it, the click dispatches an edytor-block-activate event instead (see below).",
    },
    handle: {
      type: "Snippet<[BlockHandleSnippetPayload]>",
      description: "Replaces the + and the grip with your markup. See Custom handle below.",
    },
  }}
/>

The configuration is read when the editor mounts. `blockDnd={false}` is a deprecated alias of `blockHandles={false}`; `blockHandles` wins when both are set.

You can also build the plugin yourself and list it in `plugins`: `blockHandlesPlugin` is the default, `createBlockHandlesPlugin(options)` takes the same options as the prop. The editor recognizes either one and does not add a second set of handles. When `blockHandles` is an object, it replaces any handle plugin in the list.

## Handles

A handle sits in the editor's overlay layer, left of its block, aligned with the block's first line of text. For an island block it aligns with the block's header (a direct child marked `use:block.void`, such as the code block's header), and for a void block with the top of the block. Handles follow layout changes, moves and scrolling.

- A handle exists only for blocks that can move, and is hidden while the editor is readonly.
- Handles mount lazily, for blocks within about one screen of the viewport and for blocks that are hovered, selected, focused or being dragged. Large documents do not pay for a handle per block.
- A handle is transparent until you hover its block, and its block stays hovered while the pointer goes from the text to the handle and rests on it (the handle sits flush with the block). On touch devices (no hover), handles are always visible.
- In a column's gap a block's handle sits flush with the block, as wide as its buttons, and its box covers the block's whole row: a pointer anywhere in it hovers the block, shown or not, so the grip is reached from any side, as in Notion. The rest of the gap is the column resize strip: its left part, and the height no block's row of that column covers. Column 1's handles sit in the editor's gutter, over no strip, as a root block's do.
- The buttons are gray (`#ada9a3`) with a 6px-rounded hover background.

### The + button

Clicking `+` opens the [slash menu](/docs/plugins/slash-menu#from-the-block-handle) below it and adds nothing yet: the menu has its own search field. Picking a kind inserts a block of it below the block (above with <kbd>Alt</kbd>) with the caret in it, as one undo step. For a block directly in a column, <kbd>Alt</kbd> adds a column instead, right of the block's column, holding the new block (as Notion: one `edytor.moveBlocks` with `position: 'right'` in the same undo step). Typing filters the menu, never the document. The kind lands where it fits, as the slash menu places it: beside a list's item, a heading splits the list after the item and a list's own kind adds an item; a divider or code block follows the block. <kbd>Escape</kbd> closes it with the document and the undo history unchanged and the caret where it was, and so do a press outside the menu (the press then places the caret), focus leaving the menu and the editor turning readonly. A `+` clicked while the selection is still the block selection a grip click made (its menu open, or closed on a divider) gives back the selection held before the grip was clicked (a text caret when there was none), so <kbd>Escape</kbd> never leaves the grip's block selection for the next key to replace. The menu lists only the commands that can run in the block being added ([From the block handle](/docs/plugins/slash-menu#from-the-block-handle)). A plugin's veto of the insertion adds nothing, and `edytor.dispatcher.last` reads `refused`. When the block is already an empty block of the parent's default kind, the picked kind converts it instead of adding another. Without the slash menu, `+` inserts an empty block of the default kind at once and puts the caret in it. The button does nothing in a readonly editor.

The `+` dispatches `BLOCK_ADD_EVENT` (`'edytor-block-add'`, detail `{ block, anchor, insert }`, a `BlockAddition`) on the editor's root. A menu of your own answers it with `event.preventDefault()`, and calls `insert(then?)` once the user picks: it adds the block, puts the caret in it and runs `then`, as one undo step. The addition and `then`'s writes are one transaction. When `then` answers `false`, or the command it runs is refused (by the document or an extension's veto) before changing anything, `insert` takes the block back inside that transaction and answers `false`: the document, its undo and redo steps and the selection are as they were.

### Custom handle

A `handle` snippet replaces the `+` and the grip of every handle. The plugin keeps placing it beside the block's first line, showing it on hover and mounting it lazily. The snippet receives a `BlockHandleSnippetPayload`:

<TypeTable
  type={{
    block: { type: "Block", description: "The block's handle." },
    grip: { type: "action", description: "use:grip makes an element the grip: dragging (when draggable), a click that selects the block and opens its menu, and the Alt+arrow moves while it has focus." },
    add: { type: "(alt?: boolean) => void", description: "What + does: the slash menu offers what to add below (with true, Alt+click: above, or for a block directly in a column a new column right of its column); nothing is added until a row is picked." },
    readonly: { type: "boolean", description: "The editor is readonly: hide your buttons." },
    draggable: { type: "boolean", description: "Pointer dragging is on." },
  }}
/>

```svelte title="Editor.svelte"
<script lang="ts">
	import { Edytor, type BlockHandleSnippetPayload } from 'edytor';
</script>

{#snippet handle({ block, grip, add, readonly }: BlockHandleSnippetPayload)}
	{#if !readonly}
		<button onmousedown={(event) => event.preventDefault()} onclick={(event) => add(event.altKey)}>+</button>
		<button use:grip aria-label={`Move ${block.type} block`}>⠿</button>
	{/if}
{/snippet}

<Edytor blockHandles={{ handle }} />
```

The same snippet works with `createBlockHandlesPlugin({ handle })` in `plugins`. Your markup renders inside the handle's host, `[data-edytor-block-handle-host]` (a flex row right-aligned to the block's left edge, which carries the hover fade), without the buttons' built-in styles. Keep `preventDefault` on the `+` button's `mousedown`, so the click does not move the caret first.

## Drag and drop

Drag and drop uses Atlassian's [Pragmatic drag and drop](https://atlassian.design/components/pragmatic-drag-and-drop/about) and its [auto-scroll](#auto-scroll), and its drop zones use the [list item hitbox](https://atlassian.design/components/pragmatic-drag-and-drop/optional-packages/hitbox/about) (`@atlaskit/pragmatic-drag-and-drop-hitbox/list-item`), following its tree guidance: each level of the tree is a list, and an expanded item offers no "after" on its own row. While you drag, each block is a drop target. As in Notion, the hitbox splits the block's own row (not its children) into two halves, and the pointer's horizontal position decides nesting and the level:

| Pointer position | Drop |
| --- | --- |
| Top half of the row | Before the block |
| Bottom half, left of the nest threshold | After the block, as a sibling |
| Bottom half, more than one nesting step right of the block's text start | Inside it, as its last child |
| Bottom half of a block whose children show (not a closed toggle), one of them not dragged | Before its first child not dragged: the bar under the block's text, indented to that child's column, never below the whole subtree |
| Bottom half of the last block of a nested group, or the gap below it | After the block or one of the ancestors it ends: the level whose text column is nearest the pointer, one level per nesting step to the left, down to the root |
| Bottom half of a block every shown child of which is dragged, or the rows those children leave under it | The same levels, from the block's own down to the root: dragging a nested block's only child out below its parent works even when the parent is the last block at every level. Never inside the block when only its children are dragged: they would stay put |
| In the handle column left of the editor's blocks (the drag's handle width), at any row's height | The row there, by its halves as above, the pointer's horizontal position picking the outermost level, but only before or after a block, never inside one (over a list's first item whose other placements are refused, nothing); between two rows the bar shown stays, so a drag straight down or up the handles reorders row after row. A block reaching into the column (a list item's marker) hands the pointer to this rule, so no placement of a row passed on the way is held |

The nest threshold is the block's first text line's start plus one nesting step: `--edytor-nest-indent` in px (see [Nested blocks](/docs/customization/styling#nested-blocks)), else 24px. So in the lower half of a row, move right to nest and back left to drop beside it; below the last child of a nested group, move left to drop it one, two or more levels out. The bar is indented to the chosen level, and the [nest backdrop](#the-nest-backdrop) shows on that level's parent (none at the root). A closed toggle's children do not show, so its lower half is after it, and moving right nests at the end of its body (the toggle opens on the drop). Nesting never takes a band of the row: the two halves keep the whole height, so the gap between two blocks stays easy to hit. Pointed beside a nested block, over its ancestors' indent, the pointer is on that block's row. While you drag, the other blocks' handles let the pointer through to the blocks under them.

Only placements the document allows are offered: a block that cannot hold children (a divider, an image) never nests, a level where the blocks do not fit gives way to the next nearest, and a half the document refuses entirely is the hitbox's `blocked` operation: the drop takes the other half's placement, and the indicator carries `data-blocked="true"`. The dragged blocks' own rows and their children offer nothing, so letting go over them changes nothing (as in Notion), even for the last block of a nested group, whose levels would otherwise move it out of its parent. The one exception is a parent they leave with no other shown child: their rows are then the gap under that parent's row, and offer its levels. A short gap between blocks keeps the last valid placement (its row and half; the pointer's horizontal position still picks nesting and the level), so the indicator does not flicker, from a nested block's row too. Below the document's last block the placement stays however far down you go, as in Notion: move left or right there to pick the level, and let go to drop at the end of the document; leaving the editor's width clears it. Another block's own row never keeps it, so dragging up from a child onto its parent's row targets the parent. A list container has no row of its own, so its padding counts as a gap: overshooting a list's first item keeps "before" that item.

### Dragging several blocks

As in Notion, dragging the handle of a block the selection covers moves every block it covers, together:

- **A block selection**: its blocks as clicked (a selected list is one block: dragging one of its items, or pressing <kbd>Alt</kbd> + an arrow on the item's handle, moves that item alone, as with a selected paragraph's child).
- **A text range across blocks**: every block it spans, as <kbd>Tab</kbd> and Turn into read them (a list the range only enters counts through the items it spans; a code block's lines count as the code block).

The outermost of those blocks move, in document order, wherever they sit: their children, and a closed toggle's hidden body, travel with them. The [drag preview](#the-drag-preview) shows them all with a count badge, and the drop indicator carries the same count (`data-count` on `[data-edytor-drop-indicator]`, with a `[data-edytor-drag-count]` badge in the gutter). While the drag lasts the moving blocks are block-selected (a text range becomes the block selection of the blocks it covers, and stays so when the drag is cancelled), and after the drop they stay selected (a moved block's selected children too). The drop is one `edytor.moveBlocks` call, one undo step: the document's rules apply to the whole group, so a placement where one of them does not fit (a paragraph directly in a list) is not offered, and a refused or vetoed move moves none of them. A block a collaborator deletes during the drag is left out. Undo puts the blocks back and restores the selection you had before the drag (the text range, or the caret), redo the moved blocks' selection.

Dragging the handle of a block outside the selection moves that block alone and selects it (a parent's handle while only its child is selected: the parent alone). A single drop is one undo step too.

After a drop the editor holds the keys, as in Notion: its root takes the focus (without scrolling, and without placing a caret: the moved blocks stay block-selected), so <kbd>Mod</kbd>+<kbd>Z</kbd> undoes the move at once, and <kbd>Mod</kbd>+<kbd>Shift</kbd>+<kbd>Z</kbd> redoes it, even when the undo gave back no selection (a drag started with none). Resizing columns does the same.

### The drag preview

As in Notion, every handle drag shows a copy of the dragged blocks under the pointer, rendered as they look in the editor, never the grip alone: for one block, one selected block, or every block of a several-block drag in document order with a `[data-edytor-drag-count]` badge in its corner. Each block's rendered element is cloned with its whole subtree (its children, a toggle's shown body) when the drag starts, and removed once the browser has taken its picture, as Pragmatic drag and drop's `setCustomNativeDragPreview` does.

- **Look**: the blocks' own look, only scaled down to 0.8 from the top left: no card, background, shadow, border radius, opacity or fade is added (the browser applies its own drag-image translucency). The blocks are laid out at their own width (the widest of them, at most 600px: a block in a column keeps its column's width), the ghost is sized to the scaled box so the browser crops nothing, and content past 300px is cut cleanly. The count badge is the one addition. The pointer keeps its place on the first block, where you grabbed it.
- **Theme**: the clones sit in a wrapper, `[data-edytor-drag-preview]` (with `data-count`), that carries the editor root's classes and its `data-edytor` attribute inside its ancestors' classes, with the root's text style and CSS variables. Theme rules such as `.edytor-notion [data-edytor-type='quote']` apply to it, and the default nesting indent too. The clones sit one level below that root, so root-child rules (the theme's leading Heading 1 as the page title) do not apply: a dragged title shows as a Heading 1.
- **Inert**: a clone keeps `data-edytor-type`, `data-edytor-children` and the kinds' own styling attributes, and loses what is editable, focusable or view-only: `contenteditable`, `id`, `tabindex`, the selected-block highlight, placeholders, render anchors, suggestions and peers' carets, and every attribute the editor finds live nodes by (`data-edytor-id`, `data-edytor-block`, `data-edytor-text`, `data-edytor-inline-block`, `data-edytor-mark`, `data-edytor-void`, …). A `[data-edytor-id]` lookup never matches it. A block's own padding and margin, which the theme sets on `[data-edytor-block]`, are copied onto its clone.

Style the ghost through `[data-edytor-drag-preview]`, for instance `[data-edytor-drag-preview] [data-edytor-type='heading'] { … }`. It is mounted under `body`, so scope rules to it rather than to the overlay.

### Beside: columns

When the document has a layout kind (the columns plugin's `columns`), a block row also has two beside bands, checked before its halves, while the pointer is within the row's height, as in Notion:

- **Right**: the row's last 15% (at least 32px), the slop past its right edge, and the page margin right of the editor (up to 120px) at the row's height, however the pointer got there. The drop puts the blocks right of the block: in a new column after its column, or, at the root, in a new two-column layout with the block on the left.
- **Left**: the page margin past the handle column (up to 120px further left) at the row's height, even entered from above or below, and, inside the editor, the 20px slop left of a row in a column (in the gap); only for a block at the root or directly in a column (a nested block keeps the pointer's horizontal position for its levels). The blocks go first. The handle column itself (as wide as the drag's handle, left of the blocks' text) is never a beside band: there the row at the pointer's height takes the drop before or after it, by its halves, row after row, gaps between rows included, so a drag straight down the handles reorders.
- **The gap between two columns**: a new column between them.

Beside a list item or a code line, the layout wraps the whole list or code block. Beside any other block it wraps that block where it is: a toggle's or a callout's child gets its layout inside the toggle or callout (a toggle's child inside a column, where no layout may go, gets a new column beside its column instead). A band the document refuses (a whole layout dragged beside a block, since no layout goes into a column) shows nothing, and letting go there moves nothing. No band is offered where the layout would stack its columns (under 480px wide). Over a layout, only the column under the pointer is measured, and a short gap never keeps a placement across a column boundary. The bar is vertical: at the block's edge and its height, or, when the drop adds a column to a layout, the layout's height, in the middle of the gap or at the layout's edge. The drop is one `edytor.moveBlocks` call with `position: 'left' | 'right'` (one undo step that restores the selection held before the drag; the moved blocks end selected). The drag preview clones each block at its own width, so a column's block keeps its column's width.

### The drop indicator

The indicator is Notion's plain 4px bar, drawn in the overlay rather than on the block, so rounded or padded block styles cannot bend it:

- **Before or after**: the bar spans the blocks at the drop slot. Between two siblings it is centered in the gap and spans both blocks, so hovering the bottom of one block and the top of the next shows the same bar.
- **Before a first child** (the lower half of a block whose children show): at that child's top, indented to its column.
- **After an ancestor** (below the last block of a nested group): below that block's row, indented to the ancestor's level.
- **Inside**: the same bar where the new child will land (after the target's last visible child, else after its own row), indented to the child's column and running to the target's right edge. With no visible child to measure, the column is one nesting step past the target's text: `--edytor-nest-indent` in px (see [Nested blocks](/docs/customization/styling#nested-blocks)), else 24px.

Set its color with `--edytor-drop-indicator-color` on the editor or any ancestor of the blocks (the default is Notion's `rgba(35, 131, 226, 0.43)`):

```css
[data-edytor] {
	--edytor-drop-indicator-color: #2eaadc;
}
```

### The nest backdrop

When the drop will nest the dragged blocks in another block, that future parent also gets Notion's soft backdrop: a rounded tint over its own row (its own content, not its children), drawn by the same overlay layer as the bar, so block styles cannot distort it. It shows for an **inside** drop (on the target, or, inside a list, on the last item the blocks nest under), and for a before/after drop among the children of a block that is not already their parent; a before/after drop that keeps the blocks' parent, or lands them at the root, shows the bar alone. It fades in and out as the placement changes, and the drop commits the placement it showed. It is `[data-edytor-drop-backdrop]` in the overlay, with `data-shown="true"` and the parent's `data-block-id` while it applies.

Set its color with `--edytor-drop-backdrop-color` on the editor or any ancestor of the blocks. The default, also set by the [Notion theme](/docs/customization/styling), is Notion's light tint, `rgba(35, 131, 226, 0.14)`. On a dark page, set Notion's dark tint yourself:

```css
.dark [data-edytor] {
	--edytor-drop-backdrop-color: rgba(35, 131, 226, 0.2);
}
```

Give it one plain color. Avoid `light-dark()`: CSS minifiers such as lightningcss (Vite's default) rewrite it into variables that exist only beside a `color-scheme` declaration, and without one the backdrop paints nothing.

### Auto-scroll

While you drag a block, the page scrolls when the pointer nears its top or bottom edge, and so does every scrolling element around the editor (the editor too, if it scrolls), the way Atlassian's [auto-scroll package](https://atlassian.design/components/pragmatic-drag-and-drop/optional-packages/auto-scroll/about) (`@atlaskit/pragmatic-drag-and-drop-auto-scroll`) does it:

- **Speed:** the closer the pointer is to the edge, and the longer it stays near it, the faster it scrolls, up to a limit, and at the same speed on 60 Hz and 120 Hz screens.
- **Which element:** the innermost scrolling element under the pointer scrolls first, then the ones around it, one per direction.
- **Scope:** it reacts only to this editor's block drags. It is registered when a drag starts and released when it ends, so a page with several editors, or other drag and drop, is unaffected.

There is nothing to configure. The browser's own drag scrolling at the window's very edge still applies on top, as no page can turn it off.

## Keyboard moves

While a handle has focus, <kbd>Alt</kbd> with an arrow key moves its block:

| Keys                           | Move                                                                 |
| ------------------------------ | -------------------------------------------------------------------- |
| <kbd>Alt</kbd> + <kbd>↑</kbd>    | Up: before the previous sibling, or before the parent from a first child |
| <kbd>Alt</kbd> + <kbd>↓</kbd>    | Down: after the next sibling, or after the parent from a last child  |
| <kbd>Alt</kbd> + <kbd>→</kbd>    | In: the last child of the previous sibling                           |
| <kbd>Alt</kbd> + <kbd>←</kbd>    | Out: after the parent (a list's item leaves the list, [as Shift+Tab](/docs/customization/hotkeys#enter-and-backspace-by-role)) |

The handle claims every <kbd>Alt</kbd>+arrow while it has focus. A handle of a block the selection covers moves the same blocks a drag of it would ([Dragging several blocks](#dragging-several-blocks)), and they end selected as after a drop: a block selection holding them stays, a text range over them stays as it was (as with <kbd>Mod</kbd>+<kbd>Shift</kbd>+arrow), and a block moved alone is selected alone. Undo restores the selection you had. As a relative step, they must share one parent, else nothing moves. A move never puts a block directly in a list it is no item of, but a block already there (an image a merge left among the items) moves among them like an item, by key, menu or drag. A move never hides a block you saw: moving a block into a closed toggle, with <kbd>Alt</kbd> + <kbd>→</kbd> or a drop inside it, opens the toggle, as <kbd>Tab</kbd> does. To move the caret's block from the text, or a block selection, see [Arrow move](/docs/plugins/arrow-move).

## Building a block menu

The [block menu plugin](/docs/plugins/block-menu) is a complete Notion-style menu: list `blockMenuPlugin` and leave `onActivate` unset. When no `onActivate` is passed, a grip click dispatches a DOM event on the editor's root, which that plugin (or your own) listens for. A menu that takes the keyboard answers it with `event.preventDefault()`. Unanswered (no menu), the editor takes the focus, so the keys act on the selected block as in Notion: <kbd>Backspace</kbd> deletes it, <kbd>Shift</kbd>+arrows extend the selection, typing replaces it. (The grip keeps its <kbd>Alt</kbd>+arrow moves while it has focus, from <kbd>Tab</kbd>.)

```ts
import { BLOCK_ACTIVATE_EVENT, type BlockActivation, type Plugin } from 'edytor';

export const myMenuPlugin: Plugin = () => ({
	onEdytorAttached: ({ node }) => {
		const open = (event: Event) => {
			// The menu takes the keyboard; without this the editor takes the focus.
			event.preventDefault();
			const { block, anchor } = (event as CustomEvent<BlockActivation>).detail;
			// Open a menu for block, next to anchor.
		};
		node.addEventListener(BLOCK_ACTIVATE_EVENT, open);
		return () => node.removeEventListener(BLOCK_ACTIVATE_EVENT, open);
	}
});
```

To build your own menu instead, pass `onActivate`. It gives you the block and the grip element; the click has already selected the block. A typical menu converts or moves the block with the editor's commands and then returns the caret to the text:

```ts
import type { BlockHandleActivation } from 'edytor';

const onActivate = async ({ block, anchor }: BlockHandleActivation) => {
	const { edytor } = block;
	const rect = anchor.getBoundingClientRect();
	// Show your menu at rect.right, rect.top, listing edytor.kinds and move actions.
	// For example, "Turn into heading 2": the kind's command converts what the
	// click selected, a selected list's items too (a list itself never converts).
	await edytor.runCommand('block.heading2');
	// Or "Move down":
	if (edytor.canMoveBlocks({ blocks: [block], direction: 'down' })) {
		edytor.moveBlocks({ blocks: [block], direction: 'down' });
	}
};
```

The same `edytor.moveBlocks` and `edytor.canMoveBlocks` calls move blocks from anywhere, with `direction` (`up`, `down`, `in`, `out`) or with a `target` and `position` (`before`, `after`, `inside`). Like the handles, `moveBlocks` opens a closed toggle the blocks land in, or that takes blocks as children, so a moved block is never hidden. See [Commands](/docs/editor/commands).

A click leaves a block selection behind, and a DOM range alone does not replace it. To put the caret back in the block after a menu action, call `setAtTextOffset` once — it replaces the block selection and the projector draws it after the flush — then focus the editor. A kind whose own content is not displayed (a list container) takes the caret in its first child:

```ts
const text = block.firstText ?? block.children[0]?.firstText;
if (text) {
	edytor.selection.setAtTextOffset(text, 0);
	edytor.node?.focus({ preventScroll: true });
}
```
