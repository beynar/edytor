# Layouts and tables

The two kinds whose children display side by side or in a grid: layouts (the columns plugin) and tables (the table plugin), as the index displays them and the gestures write them. Where to fix a wrong display is in [AGENTS.md](../../AGENTS.md) ("Where to fix what").

## Layouts

- **Layouts (`layout.*`, `docs/columns-plan.md`).** A kind whose role says `layout: true` (the columns plugin's `columns`) has its `defaultChild` (a `column`) as its item kind; no core code names either. The index displays a layout by four read-time rules: it shows only its items (another child shows right after it, `layout.only-items`), an item showing no child does not show (`layout.empty-item`), a layout showing one item or none shows as that item's children (`layout.single`), an item outside a layout shows as its children (`layout.bare-item`); every write that would leave one of these states writes what the rule shows in the same plan (`emptying`, then `dissolving`), at the rank the rule reads (`promotedRank`). Merges cross items in reading order (`layout.merge`); no layout goes into an item by any gesture (`layout.nest`: `fits`, `canPlace`), but one a race leaves there shows as it is. `placeBeside` and `wrapInLayout` are the two layout-making ops; a flow over a column's selected blocks fills their slot first (`layout.flow-slot`). The fuzz holds the `layout-shape` invariant. The roles are in `defaultSemantics`, so the room and headless documents display layouts as views with the plugin do; the plugin itself is opt-in.

## Tables

- **Tables (`table.*`).** A kind whose role says `table: true` (the table plugin's `table`) has its `defaultChild` (`tableRow`, a container) as its row kind, whose `defaultChild` (`tableCell`, a text island) is the cell kind; no core code names them.
  - The columns are data: the table's `data.columns` (`{ id, width? }`, a fine-grained array) in order, each cell's `data.column`; a column move is one `order` patch, no cell moves.
  - The index's layout pass runs the table rules (`tableVisit` in `crdt/text/index/layout.ts`): a cell displays only in a row of a table, for a listed column, first per column (else it dissolves, with its text: `table.cell`) — or, withdrawn by an undo while it holds another writer's text (`hist.undo.withdraw`: the undo of a column insert took its column out of the list), for its unlisted column, shown after the listed ones in one order (`unlistedRank` in `crdt/tables.ts`, which `cellRank`, `tableGrid` and the view share; a shell flip of a cell re-places it, `noteShell`) — a row only in a table and while it shows a cell, a table while it shows a row; a row's cells take their column's position as their display rank (`cellRank`, the `slotRank` ownership hook), and a change of the table's columns or a cell's column re-places them (`tableFacts` in the fold).
  - A row showing no cell for a column is padded by the view only (`tableGrid` reads `null`, the plugin renders a placeholder, `fillTableCell` creates it); no replica writes a cell for having seen one missing.
  - Ops are prepared plans (`crdt/doc/table.ts`): row insert (a run rank), rows delete (subtree), column insert/delete/move, row move, fill; a table listing no columns adopts them in the op's plan, with ids from their positions (`c1`, `c2`, …: concurrent adoptions write the same array items and cells' columns).
  - Column writes address the stored array's entries (the first naming a column, by item id for a delete or a width), never a position in the deduplicated list; filling a shown unlisted column lists it again, last.
  - A cell never moves (`canPlace`), merges (`canMerge`) or splits (`splitBlock`): Enter is a line break (`insertParagraph`), Backspace at its start stays, a range keeps every cell it crosses and every ancestor of its end, deleting the text it covers in each (`table.range` in `rangeDelete.ts`), a flow into a cell joins its text (`table.paste` in `flow.ts`).
  - In a view, ArrowUp/ArrowDown leave a cell only from its first/last line box (`verticalFrom` in `plugins/table/table.ts`; a wrap offset counts on the line away from the edge, so a doubt leaves the key to the browser), an empty cell shows no placeholder (`placeholderAt`, by role), and the block menu's row and column rows act at the cell the caret was last in (`TableChrome.cell`).
  - The fuzz holds `table-shape`; the corpus runs a `tables` lane.

## Selecting across columns

- **A mouse selection across a column's edge selects blocks** (`sel.drag.across-columns`, Notion): while `selection.dragging` (a drag, or a Shift+click extending its range) and the native range has one end in a column and the other not in that column (another column, or outside the layout: the ends' enclosing columns differ), the adopter (`applySelectionSnapshot`) selects the blocks `acrossColumns` (`selection/replaceSelection.ts`, from the roles) answers — every shown block from one end to the other in reading order, never a layout or a column, so a full sweep lifts (`liftLayouts`) — with cause `dom`: the projector writes nothing under the drag, the browser keeps extending its range (back with both ends in the same columns the drag is a text range again), and the root's `data-edytor-selection="blocks"` (`components/Edytor.svelte`) hides its highlight. The release keeps the blocks and asks one display, which clears that range; a Shift press's range is read again at the release (Chromium delivers its `selectionchange` after it). A range over a whole layout from above to below it and Shift+arrows stay text ranges; never decide this in the projector or a plugin.
