## Open units of work

Each unit merges the same problem when it was reported in several areas. The severity shown is the highest one a verifier confirmed.

### AW-01 — Turn into with Divider or Code places a non-item directly inside a list

- **Area:** Code organization. Also reported as low in Editing behaviors and API ease of use.
- **Severity:** medium (verified in Code organization). Low in the other two areas.
- **Effort:** S
- **Location:** src/lib/kinds.ts:140 (the `if (parent && (after || bare))` branch at :138-154)
- **Failure:** The branch for kinds that replace or follow the block runs before the list-item lift and returns early. Its slot is `{ parent: list, index: block.index + 1 }`, so the new block lands inside the list. Results on `ul[a, b, '' (e), c]`:
  - Divider on b gives `ul[a, b, divider, list-item '', list-item '', c]`.
  - Divider on e, or typing `---` in e, gives `ul[a, b, divider, list-item '', c]`.
  - Code on b gives `ul[a, b, code[codeLine], list-item '', c]`.
  - Code on e gives `ul[a,b] code ul[c]`, which is correct.

  The same command therefore places the block two different ways. This contradicts concepts/blocks.mdx:83 ("A list holds only its items… An item turned into another kind leaves the list"), the List item row in hotkeys.mdx:38, and the ZW-01 done-when.

- **Fix:** When `block.isListItem`, send the replacing and bare cases through the same lift plan the other kinds use. Lift the item out first, then retype it or insert after it outside the list. Also decide where the caret paragraph (`next`) goes at the new level.
- **Done when:** wave9-behavior-lists has rows for Divider and Code, on an empty item and on an item with text, through Turn into, the slash menu and the markdown shortcut. No list container holds a divider or a code block after any of them.

### AW-02 — Tab or Shift+Tab over a text range that enters a list treats the list container as selected

- **Area:** Editing behaviors
- **Severity:** medium
- **Effort:** S
- **Location:** src/lib/session/bindings.ts:159 (`nest`, and `moveRoots` at :133-143)
- **Failure:** `getSelectionBlocks` returns `state.blocks`, which includes the list container the range enters. `outermost` then keeps the container and drops its items. Repros:
  - (a) `[p a>[p m], ul[c,d]]`, range m..c, Shift+Tab gives `[p a, p m, ul[c,d]]`. Block-selecting the same rows gives `[p a, p m, p c, ul[d]]`.
  - (b) `[ul[a,b], ul2[c,d]]`, range b..c, Shift+Tab: b leaves its list and c does not.
  - (c) `[p a, p m, ul[c,d]]`, range m..c, Tab nests the whole list, including the unselected d.

  This breaks the hotkeys.mdx:22-23 promise that "the blocks a text selection spans" move together.

- **Fix:** For a text range in `nest`, drop containers that are not block-selected before `moveRoots`, using the same filter as `convertedBlocks`.
- **Done when:** rows next to the ZW-07 rows cover Tab and Shift+Tab over paragraph..first item and over item..item across two lists, and each result equals the result for the same rows block-selected.

### AW-03 — A vetoed Turn into on an item of a list nested directly in a list still lifts the item and reports `applied`

- **Area:** API ease of use. Also reported in Code organization, Editing behaviors and Documentation.
- **Severity:** low (confirmed in all four areas). It is the reason for API's −0.1.
- **Effort:** M
- **Location:** src/lib/kinds.ts:168
- **Failure:** The loop `while (block.isListItem && inner()) if (!block.unNestBlock()) return;` dispatches each inner lift as its own operation, and each one commits. Only after that does the plan that a setBlock veto can refuse run. The results:
  - On `u[u2[b,c], d]` with setBlock vetoed, Mod+Alt+2 at c gives `u[u2[b], c, d]`, and `dispatcher.last` is `{unNestBlock, applied}` because of the ZW-07 rule.
  - `convertToKind` returns false even though the document changed.
  - With markdownShortcuts, the dispatcher lead composes into the first lift, so typing `# ` deletes the typed '#' and lifts the item.

  This contradicts kinds.ts:161, plugins/operations.mdx:70, markdown-shortcuts.mdx:49, block-menu.mdx:87 and migration.mdx:192.

- **Fix:** Prepare every inner lift and the final unNest+set as one `facade.compose` plan (loop over `prepare.unNestBlock`), and dispatch it once so a veto refuses all of it and the lead composes into the conversion.
- **Done when:** a veto row next to DR-behavior-2 covers the hotkey, convertToKind and markdown paths. In each, the tree is unchanged, `last` is refused, and `# ` stays as text.

### AW-04 — A concurrent outdent of a middle item plus a lift or outdent of a neighbour leaves a bare paragraph inside a list

- **Area:** CRDT correctness
- **Severity:** low (proposed as medium; the verifier downgraded it)
- **Effort:** M (S if the case is only documented and pinned)
- **Location:** src/lib/crdt/edytor-doc.ts:1870 (ZW-03 branch of unNestBlocks, :1850-1871)
- **Failure:** The ZW-03 split writes an explicit `move(before, head, 0)` for each leading item. That races with a peer's move of I1 to the root, and the peer's retype to paragraph also sticks. Converged outcomes on some client-id assignments:
  - `unNestBlock('I2') ‖ mergeBackward('I1')` gives `NEW:unordered-list[I1:paragraph] I2 U[I3]`.
  - `unNestBlock('I2') ‖ unNestBlock('I1')` gives the same shape.
  - In a four-item list, `unNestBlock('I3') ‖ unNestBlock('I2')` gives `NEW:unordered-list[I1:list-item,I2:paragraph] …`.
  - `unNestBlock('I2') ‖ deleteBlocks(['U'])` also gives it.

  The trailing-side version already existed before wave 9 and also broke text order. Wave 9 fixed the ordering and moved the race to the leading side. No text is lost and every replica converges. The contract at :476-500 does not list this outcome.

- **Fix:** Add a read-time rule in runs.ts `typeOf`: show a block stored as the default kind whose display parent is a list as that list's item. This closes this case, the old trailing-side case and the documented "concurrent undo of a retype" residual. Alternatively, add the case to the residual list in the contract and pin it.
- **Done when:** converge rows for every scenario above pass. wellFormed or the CONTAINERS campaign checks that no default-kind block sits directly in a list, or the contract lists the residual and a row pins it.

### AW-05 — An island's lines shed into a columns layout are retyped to `column`, which hides their text

- **Area:** CRDT correctness
- **Severity:** low
- **Effort:** S
- **Location:** src/lib/crdt/edytor-doc.ts:1670 (island branch of `settledKind`, :1664-1678)
- **Failure:** `kind = defaultChild(parent)` has no `rendersContent` guard, and `fitted` keeps 'column'. Deleting column K2 and then the code block X gives `C:columns[K1[A], Xl:column]`, with "let x" invisible and not editable. `setBlockType('X','divider')` does the same. The concurrent run shows `Xl:paragraph`. This violates contract :446-449. It needs a custom container whose default child renders no content; none ships.
- **Fix:** Use `rendersContentOf(defaultChild(parent)) ? defaultChild(parent) : defaultChild(null)`, the same fallback as `typeOf` (ZW-06).
- **Done when:** a rescore6 row next to the ZW-06 row shows the sequential and concurrent runs ending with the same content-rendering kind.

### AW-06 — A non-item the editor shed into a list cannot be reordered within that list

- **Area:** CRDT correctness. Also reported in Code organization.
- **Severity:** low
- **Effort:** S
- **Location:** src/lib/crdt/edytor-doc.ts:1149 (`canPlace`, :1139-1151)
- **Failure:** `canPlace` applies `fits` even when the destination is the block's current parent. After `mergeBackward('I2')` on `U[I1, I2[IMG], I3]` gives `U[I1, IMG, I3]`, moving IMG within U is refused, and so is moving IMG together with I3. `canPlace(['IMG'],'U')` is false while `canPlace(['IMG'])` is true. Alt+Shift+Up/Down, the menu's Move up/down and a drag within the list all do nothing, while neighbouring items still move.
- **Fix:** Treat a block whose current parent is already `parent` as fitting, since reordering does not change what the list holds. Or document the refusal next to DR-crdt-1 in the contract and block-handles.mdx.
- **Done when:** a row pins either the allowed reorder of a shed image within its list, or the documented refusal.

### AW-07 — Tab after a list whose last child is a void or island is silently refused

- **Area:** Editing behaviors
- **Severity:** low
- **Effort:** S
- **Location:** src/lib/crdt/edytor-doc.ts:1204 (`nestParent`)
- **Failure:** `nestParent` stops at the first child that `fits`, which is the image, and `canPlace` then refuses a void or island parent. `[ul[li a, image], p q]` with Tab at q is refused, and so is the pinned DR-crdt-1 chain. The docs (hotkeys, document-api, commands, contract :424) say Tab after a list nests under its last item. `position: 'inside'` drops go through the same `nestParent` (moves.ts:53) but were not verified.
- **Fix:** Walk back to the last child that can hold children, or fall back to the previous sibling, before refusing. Or document the exception.
- **Done when:** a row next to the ZW-01 Tab rows passes for a list ending in an image, with the inside-drop path checked too.

### AW-08 — Pasting a bulleted or numbered list into a structural list keeps flat item kinds inside it

- **Area:** Editing behaviors
- **Severity:** low (proposed as medium; the verifier downgraded it)
- **Effort:** S
- **Location:** src/lib/crdt/edytor-doc.ts:1192 (`fitted`), used by flow.ts:61/111/119
- **Failure:** `fitted` maps only the default kind to the list's item. Pasting `<ol><li>x</li><li>y</li></ol>` at bb@1 in `ol[a, bb, c]` gives `ol[list-item a, list-item bx, numbered-list-item yb, list-item c]`. With notion.css the list reads "1. a / 2. bx / 1. yb / 3. c". Wave 9's `itemKind` says these flat kinds are the list's own items, so Turn into and paste disagree. Structural lists come only from JSON, the API or a fragment.
- **Fix:** Treat a line whose kind is the destination list's `itemKind` as that list's item. `itemKind` is view data today, so pass the mapping in via FlowContext or add it to the semantics.
- **Done when:** a SW9-containers-1 row for pasting `<ol><li>` or `<ul><li>` into the middle of an item gives only `list-item` children.

### AW-09 — ZW-11 is only half done: the DST corpus has no lists, and deleteOracle models neither `emptiable` nor the rescue retype

- **Area:** CRDT correctness

### AW-10 — The next.0 upgrade note's "no `/`, `%`, `?` or `#`" rule misses backslash, tab and newline ids

- **Area:** Collaboration. Also reported in Documentation.
- **Severity:** low
- **Effort:** S
- **Location:** site/content/docs/reference/migration.mdx:136 (pinned at src/tests/docs-drift.test.ts:248; also troubleshooting.mdx:85)
- **Failure:** next.0 put the raw id into a ws/wss URL. There, `\` is read as `/`, so the quick-start route answers 404, and tab, CR and LF are stripped, so the client opens a different room. The note says a decoding Worker unifies every id without those four characters, which is false for these ids. The raw-routing troubleshooting row names only `:`, `@`, `+` and `,`, while next.0 also sent `;`, `=`, `&`, `$`, `[`, `]` and `|` raw.
- **Fix:** Name `\` next to `/` in the list of ids that never reached their room, and say that tab and newline are stripped. Make the troubleshooting row say "any character encodeURIComponent escapes". Relax the drift row to match.
- **Done when:** the note and the troubleshooting row match the WHATWG URL behaviour, and docs-drift passes with the new phrase.

## Refuted

No finding was refuted outright. Every reported finding was confirmed, and two were downgraded:

- **CRDT, concurrent outdent leaves a paragraph in a list (AW-04): medium to low.** It is not a clean regression. Before wave 9 the same race happened on the trailing side, and it also broke text order. Wave 9 moved it to the leading side and now keeps order in every case. It needs two peers editing neighbouring items within the sync window, loses no text, and converges.
- **Editing behaviors, list paste keeps flat item kinds (AW-08): medium to low.** Structural lists never come from the bundled UI, markdown shortcuts or HTML paste. The model stays well-formed, and the documented rule that "other kinds keep their kind" literally covers the case.

With these two downgrades, CRDT moves from band 4.3 to 4.7, and Editing behaviors stays at 4.3 instead of dropping to 4.0.
