# Release, docs and packaging

How the docs site, the packed tarball, the npm release and the deploys fit together. [AGENTS.md](../../AGENTS.md) is the overview; this file holds the release rules.

- Docs: the site (`site/content/docs`) is the single source for API and behavior; the README is a landing page that links to it. Getting-started routes mount editable editors client-only, `reference/platform-support` names what the browser lanes run (update it with Playwright or the device list) and `server/internals` lists the room's alarm tasks and tables: `src/tests/docs-onboarding.test.ts` checks all three against the code. A page leads with the common case and keeps edge cases in tables, callouts or an "Edge cases" list; no prose line outside a table or a code block is over 1,200 characters, `collaboration/concurrent-editing` states each rule as an Alice and Bob table and each race in one table only, no callout holds a table, and a restructured passage keeps the meaning it had (`docs readability` in `src/tests/docs-drift.test.ts`).
- Install: `pnpm add edytor` from the release candidate on (npm's `latest`), the name every install instruction gives, the landing page's Copy install included; a `-next.N` pre-release is `pnpm add edytor@next` (`src/tests/docs-drift.test.ts` checks the one the version is published under).
  - Release: bump the version, run the lanes locally, deploy the site, land it on `master` (through a pull request whose `CI passed` check is green: the `master` ruleset in CONTRIBUTING.md requires it, and no one bypasses it; a version tag is pushed after the merge), then push an annotated `v<version>` tag: `.github/workflows/publish.yml` calls `ci.yml` on the tagged commit (the gate lanes and Playwright Chromium) and publishes only when it passed (npm trusted publishing with provenance, no token; `next` for a `-next.N` pre-release, `latest` for a release candidate `-rc.N` and a release).
  - The docs live at `https://edytor.dev` (the `edytor-docs` Worker's custom domain, `site/wrangler.jsonc`; the workers.dev URL still answers and the room allows both origins) and redeploy on every push to `master` through Workers Builds (the `edytor-docs` Worker's trigger "Deploy docs on master": `pnpm install --frozen-lockfile`, then `cd site && KEEP_LIVE=1 pnpm run deploy`, so a served version keeps its live tarball; `cf builds triggers`/`cf builds list` manage and inspect it).
  - Workers Builds forces every `wrangler deploy` of a build onto the connected Worker's name (`WRANGLER_CI_OVERRIDE_NAME`): the room's `deploy` script unsets it, or the room would replace the docs (it did once: `site/wrangler.jsonc`'s `v2` migration deletes the class that left).
  - The site also hosts each packed tarball: `site/scripts/pack-edytor.sh` (run by the site's `deploy`; it also copies the demo's chrome, `src/routes/chrome`, into `site/islands/chrome`, gitignored, its `$lib/index.js` imports rewritten to `edytor`, for the landing's live editor, as the package draws no chrome) stages it in `site/public/` under its versioned name, which the site serves at its root (earlier installs by URL).
  - A served tarball URL is permanent (lockfiles pin the URL and its hash): `pnpm run deploy` in `site/` refuses new bytes under a version the site already serves (`FORCE=1` overrides) and re-serves every version in `site/scripts/served-versions.txt` from the live bytes, so whenever the packed code changes, bump the pre-release version (`next.N`) and append it to that list (never remove one).
  - The deploy then reinstalls the site and the demo room `site/room` from the new pack and refuses to build unless both hold it (`site/scripts/installed-edytor.sh`: the landing's live editor and the room bundle the installed copy, not the tarball), deploys the docs to the beynar Cloudflare account (`CLOUDFLARE_ACCOUNT_ID`, as `site/room/wrangler.jsonc`) and the room (it runs the same packed `edytor/cloudflare`), and ends with `site/scripts/smoke.sh`, which rechecks both installs and also dials a closed demo room from the docs origin and requires a `4404` close (`site/scripts/probe-room.mjs`).
- Package: `pnpm package` is `svelte-package`, then `scripts/mangle.mjs`, then `publint`. The mangle shortens, in `dist/**/*.js` only (never a declaration or a component), the internal property names listed in `scripts/mangle-names.txt`, each renamed at every site. A listed name must still pass the script's rules when the package builds, or the build fails naming it: named by no declaration a consumer's types reach from `exports` (`@internal` members are stripped from them), no component of the package, string, template or regex, export or import name, `dataset` key, property signature of a `src/lib` type, dependency, the platform's lib declarations, nor the site's, the demo chrome's or the packed consumer's code; and either a class member never used as an object key, or an object key read by name that no sync-context or serializing module names (wire and stored keys keep theirs). `node scripts/mangle.mjs --write` rewrites the list from the rules (review its diff like the API report), `--check` checks it against the current `dist/`. The lanes run `src/`: `tests/packed-consumer/run.sh` (and the site's install) is what runs the shortened build.
- The API reference pages (`site/content/docs/reference/api/*.mdx`) are generated by `pnpm api:report` from the published declarations and their JSDoc, beside the reports; `pnpm check:api` fails when one is stale. Edit the JSDoc, never the pages.
