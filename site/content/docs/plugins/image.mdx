`createImagePlugin()` adds Notion's image block: an "Add an image" panel (your `empty` snippet, `createMediaEmptyPlugin({ empty })`) until the block has a source, then the image with an editable caption. Hovering the image, or selecting its block, shows handles to resize it and a toolbar to align it and set its alt text. `<Edytor>` includes it by default, so the slash menu lists "Image" under `Media` without any setup. List the uploads plugin, `createUploadsPlugin({ upload })`, and pasted or dropped image files become image blocks too.

```svelte title="Editor.svelte" check
<script lang="ts">
	import { Edytor, createUploadsPlugin } from 'edytor';

	// Optional: an Upload button next to the link field, and pasted or dropped
	// image files uploaded into image blocks (the default image plugin takes them).
	const uploads = createUploadsPlugin({
		upload: async (file) => {
			const body = new FormData();
			body.append('file', file);
			const response = await fetch('/api/uploads', { method: 'POST', body });
			return (await response.json()).url;
		}
	});
</script>

<Edytor plugins={[uploads]} />
```

An image plugin you list (any `createImagePlugin(...)`) replaces the default one. It takes links; with the [uploads plugin](/docs/editor/clipboard#pasted-and-dropped-files) listed (`createUploadsPlugin({ upload })`, the view's one uploader), files too.

## Customize

The empty block's panel (`empty`) and the toolbar over the hovered image (`toolbar`) are your snippets. Here, a dashed drop zone with a file pill and a link field, and a dark pill with three alignments and an alt field.

## Options

`createImagePlugin()` takes no options. Its chrome's parts that draw your markup are their own plugins: the empty block's panel (`createMediaEmptyPlugin({ empty })`), the toolbar over the hovered image (`createImageToolbarPlugin({ toolbar })`: the alignment buttons and the alt field at its top right, their behavior `{@attach toolbar.bar}` and `{@attach toolbar.altField}`; without it, the resize handles alone) and the uploader (`createUploadsPlugin({ upload })`). See [Menus and handles](/docs/customization/menus#image-toolbar).

## The kind

| Kind    | Element  | Data (`ImageData`)                                                   | Preset                                                        |
| ------- | -------- | -------------------------------------------------------------------- | ------------------------------------------------------------- |
| `image` | `figure` | `{ src?: string, alt?: string, width?: number, align?: ImageAlign }` | Image (🖼, group `Media`, keywords `picture`, `photo`, `img`) |

| Key     | Meaning                                                                                                                            |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `src`   | The image's source (see below). Without one the block shows the "Add an image" panel.                                               |
| `alt`   | The image's text alternative, rendered as its `alt`. None renders `alt=""` (a decorative image).                                    |
| `width` | Its width in CSS pixels, never more than its block (`max-width: 100%`). None: its natural width.                                    |
| `align` | `'left'`, `'center'` (the default) or `'right'`: where an image narrower than its block sits. Any other value reads as `'center'`.  |

The block is void: it is not part of the text flow, takes no children and is never merged. Its only text is the caption, which stays editable. The command id is `block.image`. The kind declares no `empty` shape, so turning a paragraph into an image keeps the paragraph's text as the caption.

A source is accepted only when it is an `http:` or `https:` URL, a `blob:` URL or an inline `data:image/…` URL. Any other value, in the document or typed in the panel, is treated as no source. The check is exported as `safeImageSrc(value)` (the accepted source, or `null`), and the types `ImageData` and `ImageAlign` and the constant `MIN_IMAGE_WIDTH` are exported too. A failed `upload` shows the panel's error instead of an image.

An inline image is stored in the document itself, and every catch-up and every update that carries the block sends it again, so the plugin takes one only up to `MAX_INLINE_IMAGE_BYTES` (1 MiB of its `data:` URL). List the uploads plugin with an `upload` that stores the file and answers its URL: that is the way to add a large image.

- A larger one pasted in the link field is refused with a message that points to the Upload button (or, without `upload`, to hosting the file and pasting its link), and an HTML paste does not import it. A document that already holds a larger one still shows it.
- `storableImageSrc(value)` is the check the writes use (`safeImageSrc`, but no inline image over the cap).

:::warning
In a collaborative document, `upload` is also the way to add more than a few images: the [room's document quota](/docs/server/room#quotas) is 2 MiB by default, so two or three inline images near the cap fill it, and the room then refuses every later edit.
:::

## Empty block

Without a source, the block shows an "Add an image" button. Clicking it opens a panel with:

- a link field ("Paste the image link…"); <kbd>Enter</kbd> or the "Embed image" button sets `data.src`;
- an "Upload" button, only with the uploads plugin listed. It opens a file picker for images, calls `upload(file)` and embeds the URL it answers;
- a short error line when the link is not an accepted source.

In a readonly view the block shows a passive placeholder instead, with no button, link field or file picker, so a viewer can never start `upload`. In an editable view the write is a `src` data write (`patchData`), one undo step.

## Pasting and dropping files

With the uploads plugin, the view claims a paste or a drop that carries image files (an `image/*` type), as Notion does:

1. Each file becomes an empty image block. A pasted one goes where a pasted image goes (after the caret's line, the text after the caret moving to a new line, as for an [HTML image](/docs/editor/clipboard#where-pasted-content-goes)). A dropped one goes where the drop indicator shows while you drag it over the editor: the same line a block drag draws, between blocks, inside one or beside one, as Notion does ([Pasted and dropped files](/docs/editor/clipboard#pasted-and-dropped-files)); it never replaces a block selection. All the files of one paste or drop are one command and **one undo step**.
2. While its file uploads, your `empty` snippet shows it: the controller's `pending` is `{ status: 'uploading', progress, preview }` (`preview` a local `blob:` URL of the file, `progress` filled as `upload(file, report)` calls `report.progress(fraction)`, `null` without it), as for a media block; the demo shows it dimmed with a bar and "Uploading…". This is this view's state only: a peer sees the empty image block until the URL arrives.
3. When `upload(file)` answers, its URL fills the block's `src`. That write is kept out of the history (`dispatcher.outside`, see [History](/docs/editor/history)), so the paste stays the one step: undo removes the image, URL included, and redo brings it back whole. When the upload ends while the image is not shown (its paste undone, the block deleted), this view keeps the URL and fills the block when it shows again (a redo, an undo of the delete), still outside the history. A block that never comes back gets nothing.
4. A failed upload, or an answer that is not an accepted source, leaves the block empty, its panel open with "The upload failed: try again or paste a link." Embedding a link or an upload from that panel clears the error.

A paste whose HTML shows text (an office app also puts a picture of the copied text on the clipboard) is imported as HTML instead. A file that is no image goes to the video, audio or file kind listed, in the same paste ([Pasted and dropped files](/docs/editor/clipboard#pasted-and-dropped-files)); one no kind takes is left to your own [`onPaste`](/docs/editor/clipboard#plugin-hooks) hook (unclaimed, it inserts nothing). A readonly view ignores the paste.

## Resize, alignment and alt text

Hovering an image in an editable view shows, in the editor's overlay (never inside the editable host), the chrome below. With no image under the pointer, an image block that is the whole block selection (clicked, or selected from the keyboard) shows it too, so its alignment and alt text are reachable without hovering.

- **A resize handle on each side**, a pill at mid-height. Dragging one resizes the image live; the release writes `data.width` (whole pixels, one undo step). A centered image grows on both sides, so it changes by twice the pointer's move; a left- or right-aligned one changes by the move. The width stays between `MIN_IMAGE_WIDTH` (48 px) and the block's width. While you drag, only your view shows the new width (no peer gets a frame); <kbd>Escape</kbd> drops the drag and writes nothing, and the editor takes the keys after the release, so <kbd>Mod</kbd>+<kbd>Z</kbd> undoes it at once.
- **A toolbar** at the image's top right: Align left, Align center and Align right (each sets `data.align`, one undo step) and Alt text, which opens a field under it. Typing there writes `data.alt` as you type; the keystrokes group into one undo step, as in a field bound to `block.data` (a replaced value, or a pause past the history's capture window, starts a new one). <kbd>Enter</kbd> or <kbd>Escape</kbd> closes it and gives the keys back to the editor; a press outside the field and the toolbar, or focus moving elsewhere, closes it too, and the chrome follows the pointer again.

A readonly view shows none of this, and a drag in progress ends when the view turns readonly.

## Image and caption

With a source, the block renders the image (its `alt`, its `width`, not draggable) in a wrapper that places it by `align`, then the caption in a `<figcaption>`. With [`richTextPlaceholder`](/docs/customization/placeholder#notion-placeholders), an empty caption shows "Write a caption…" while focused.

To set the source from code:

```ts title="src/lib/set-image.ts" check
edytor.patchData(block.id, [
	{ path: ['src'], value: 'https://example.com/photo.jpg' },
	{ path: ['alt'], value: 'A red barn' },
	{ path: ['width'], value: 320 },
	{ path: ['align'], value: 'left' }
]);
```

One `patchData` is one command and one undo step, however many properties it writes.

## Clipboard

- Copying exports `<figure><img src="…" alt="…" width="…"><figcaption>caption</figcaption></figure>` (no `img` without a source, no `width` without one), with `data-align="left"` or `"right"` on the `figure` when the image is not centered.
- Pasting HTML imports a `figure` that contains an `img` with an accepted `src`, and a bare `img` with one, as an image block: its source, its `alt`, its `width` attribute (when a positive number) and the figure's `data-align`. An `img` inside a paragraph splits it around the image ([HTML import](/docs/editor/clipboard#html-import)).

## Styling

The [Notion theme](/docs/customization/styling#notion-theme) styles the block. Without it, target:

| Selector                          | Matches                                |
| --------------------------------- | -------------------------------------- |
| `[data-edytor-type='image']`      | The `figure`                           |
| `[data-edytor-image]`             | The wrapper around the `img` (`data-align`) |
| `[data-edytor-image-empty]`       | Where the empty state (your `empty` snippet) renders |
| `[data-edytor-image-resize]`      | A resize handle in the overlay (`="left"`, `="right"`; `data-dragging="true"` while it drags); its `::after` is the pill |
| `[data-edytor-image-toolbar-slot]` | Where your `toolbar` renders, at the image's top right |
| `[data-edytor-image-toolbar]`     | Your toolbar's bar (`toolbar.bar` marks it) |
| `[data-edytor-image-alt]`         | Your alt text field (`controls.altField` marks it) |

The plugin places the resize handles and their pills; the [Notion theme](/docs/customization/styling#notion-theme) paints the pills (a dark pill with a light ring, `--edytor-image-handle-color`), and without it they are unpainted. An `empty` failure is `"invalid"`, `"upload"` for a failed upload, or `"inline"` for an inline image over 1 MiB.

To change the markup, list a plugin that names the `image` kind's `snippet` (see [Restyling a kind](/docs/editor/edytor-component#restyling-a-kind)): the default image plugin comes after yours, and its other fields stay. To replace the kind itself, define every field you need in your own plugin: definitions are first-wins, field by field.
