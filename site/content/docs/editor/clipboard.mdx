Edytor handles copy, cut, paste and drop from its document model instead of letting the browser copy rendered HTML. Copies between Edytor editors keep every block, mark and inline block; copies to other apps get clean HTML and plain text; pasted HTML is mapped onto your block kinds and marks.

## Copy and cut

Copy and cut write three formats:

| Format | Content |
| --- | --- |
| `application/x-edytor-fragment` | The copied content as Edytor JSON. |
| `text/html` | HTML built from your kinds and marks, with the same JSON embedded in a `data-edytor-fragment` attribute. |
| `text/plain` | The text, one line per block. |

The embedded copy lets a paste into another Edytor editor keep full fidelity even when the clipboard drops the custom format, which some browsers and apps do.

What gets copied:

- A text range inside one block copies that text with its marks and inline blocks.
- A text range across blocks copies the blocks it touches, cut at the range's ends. A closed toggle's hidden body is copied exactly when deleting the range would delete it: with a toggle the range covers, or starts at the header of. Cut deletes the range as <kbd>Backspace</kbd> does, so a cut, or a copy followed by <kbd>Backspace</kbd>, never loses or duplicates it.
- A block selection copies exactly the selected blocks, as whole blocks: a selected list or code block with everything in it (`selection.selectedMembers`), a selected parent's unselected children left out ([Block selection](/docs/editor/selection#block-selection)).

Copy works in [readonly mode](/docs/editor/readonly) and never creates an undo step. Cut is one undo step and is ignored in readonly mode.

### How content is exported

The HTML and plain text come from the definitions, so exporting a kind looks like rendering it:

- A block kind's `html` form: a tag name that wraps the content then the children (the rich text plugin uses `blockquote` for quotes, `li` for list items), or a function of the block and its serialized content and children. The default is `<p>` around the content.
- A block kind's `plain` form, a function; the default is the content, then the children, one per line.
- A mark's `tag` and `attributes`: bold exports `<strong>`, a link `<a href>`, a color `<span style="color: …">`. A mark without a tag exports its text only.
- An inline block's `plain` function; by default an inline block exports nothing to plain text. Its `html` function gives its HTML (an [equation](/docs/plugins/equation#clipboard) writes MathML); by default it is an empty `<span data-edytor-inline-block>`.

See [Custom blocks](/docs/customization/blocks) for declaring these forms.

## Paste

A paste is handled by the first rule that applies:

1. **An Edytor fragment**, from the custom format or embedded in the HTML. Pasted with full fidelity.
2. **A plugin's `onPaste` hook**, if one calls `prevent()`.
3. **Files** (an image from the clipboard, say): ignored unless a plugin's `onPaste` handled them. The [image plugin](/docs/plugins/image#pasting-and-dropping-files) given an `upload` handles image files: each becomes an image block, uploaded.
4. **External `text/html`**, imported as blocks and marks (below).
5. **`text/plain`**, one block per line.

<kbd>Shift</kbd>+paste (<kbd>Mod</kbd>+<kbd>Shift</kbd>+<kbd>V</kbd>) pastes the plain text only and skips rules 1 to 4, plugin hooks included. Plain text takes the marks at the caret.

**Pasting a link over selected text links it**, as in Notion: with [rich text](/docs/plugins/rich-text#pasting-a-link) and a text range selected outside a code block, a paste whose plain text is one URL (`http:`, `https:` or `mailto:`) makes the selected text a link to it and keeps it selected, instead of replacing it. At a caret, a URL is inserted as a link, and undo gives the plain URL back first. This is the rich text plugin's `onPaste` hook (rule 2). Text that is not one URL, a caret inside a link or inline code, and <kbd>Shift</kbd>+paste paste as usual.

Paste is one undo step and is ignored in readonly mode. Dropping content from outside the editor follows the same rules. Dragging text inside the editor moves it: see [Dragging text](#dragging-text).

### Where pasted content goes

The same placement applies to Edytor fragments, HTML and multi-line text:

- **One line** joins the text at the caret. Into an empty block, a line of another kind gives the block its kind too (a heading pasted into an empty paragraph makes a heading), except the first line of a toggle, open or closed, or of a callout or quote with nested lines, which keeps its kind and takes the text only. A pasted line's nested lines come under the block it joins, except a closed toggle's: they go after it, so nothing lands in its hidden body.
- **Several lines** split the block at the caret: the first line joins the text before the caret, the last line takes the text after it, and the others go between. Pasting the lines `X` and `Y` into `Hello|World` gives `HelloX` and `YWorld`. The block's children go with the text after the caret to the last line; a closed toggle's hidden body stays with the first line. At the end of the first line of an open toggle, or of a callout or quote with nested lines, the nested lines stay where they are and what follows the first pasted line becomes its first nested lines, as <kbd>Enter</kbd> there opens a first nested line; when that first line is empty, it keeps its kind and takes the first pasted line's text only, even an open toggle with no nested lines yet. In the middle of that line, the nested lines go with the text after the caret.
- **A list block from an Edytor fragment, a code block, a divider or an image** never joins text: a list and a code block show no text line of their own, and a divider or an image is a block of its own (an image's caption belongs to it). It is inserted as a block, and the text after the caret moves to a new line of the same kind after it, as <kbd>Enter</kbd> splits the line (at the end of an open toggle's, a callout's or a quote's first line with nested lines, the pasted blocks lead the nested lines instead, as above). Pasting `x` and a divider into `hello| world` gives `hellox`, the divider, then ` world`. At the start of a block such content goes before it. A list or a code block replaces an empty block; after a divider or an image, the empty line stays for the caret.
- **List items from HTML** (`<ul><li>one</li><li>two</li></ul>`) are lines of their own kind, not a list block, and join like other lines: pasted at `hello| world` they give `helloone` and a bulleted item `two world`; at `|hello world`, `one` and a bulleted item `twohello world`.
- **Inside a code block** everything pastes as plain code lines: a list's items, a code block's lines and paragraphs each become one line.
- **Blocks copied from a block selection** are inserted as whole blocks after the caret's block, replacing it when it is empty.
- The caret ends after the pasted content: at the end of its last line (a list's last item, a code block's last line), or on the line after a pasted divider or image.
- With **blocks selected**, the pasted content replaces them.
- A pasted range replaces the selected text first.

Pasted blocks and inline blocks always get new ids, so pasting twice never creates duplicates. Their marks, data, children and order are kept.

## HTML import

External HTML, from a web page, Google Docs or a word processor, is parsed by the browser's `DOMParser`. Parsing is inert: no script runs and nothing loads. The import walks the result and maps elements onto the registered definitions.

**Blocks.** An element becomes a block kind when:

- a kind's `parse(element)` hook returns data for it (checked first), or
- its tag is the one a kind exports or renders for one of its presets. A void kind that has a `parse` hook (the image and the media kinds) is found by its hook only: its tag alone carries no source.

A void block takes only the text of its element's `figcaption` as its caption: an `iframe`'s fallback text, a `video`'s source list or a bookmark's link text never become content.

With the rich text plugin, that maps `h1`–`h3` to headings, `h4`–`h6` to `h3` headings, `blockquote` to quotes, `li` to bulleted items, `li` inside `ol` to numbered items, `hr` to dividers, `details` to toggles and `pre` to code blocks (one line per text line, with the code plugin). The image plugin maps a `figure` holding an `img` with a safe `src`, and a bare `img` with one, to an image block (its `alt` and `width` attribute come along). When you list them, the [embed](/docs/plugins/embed) plugin maps an `iframe` an allowlisted provider plays to an embed block, and the [video](/docs/plugins/video) and [audio](/docs/plugins/audio) plugins map a `video` or `audio` with a safe source (its `src`, or a `source` child's) to their blocks; each also takes its element inside a `figure`, with the `figcaption` as the caption. Without them those elements are dropped.

**Images inside text.** An element of a void kind (an `img`) met inside a line, even wrapped in inline markup such as Google Docs' `<p><span><img></span></p>`, ends the line there: the image becomes a block of its own, and the text after it a new line of the same kind. `<p>before <img src="…"> after</p>` gives `before`, the image, then `after`. A line left with no text around the image is not kept.

**Emoji and icons drawn as images** stay in the text as their `alt`: an `img` whose `alt` is emoji only (`<img alt="😂" src="…">`, as X and Gmail write emoji), whose class names an emoji or that has `data-emoji` (Slack, WordPress), or whose `width` and `height` are 32 px or less (an icon, an email's tracking pixel, which has no `alt` and so adds nothing). `<p>So funny <img alt="😂" src="…"> right</p>` pastes as one line, `So funny 😂 right`.

**Inline atoms.** An element inside a line becomes an inline atom when an atom kind's `parse(element)` returns data for it; its contents are then not read as text. With the [equation](/docs/plugins/equation#clipboard) plugin, KaTeX's markup or a `<math>` with a TeX annotation becomes an inline equation (a `display="block"` one, a block equation).

**Marks.** Text takes a mark when:

- the mark's `parse(element)` returns a value (checked first), or
- the element's tag equals the mark's `tag`, for marks without a value.

The rich text plugin maps `strong`/`b`, `em`/`i`, `u`, `s`/`strike`/`del`, `code`, `sup` and `sub`, links (`a` with a safe `href`), text colors, backgrounds and `mark` highlights, and the bold, italic, underline and strikethrough styles Google Docs writes on spans.

**Everything else:**

- Unknown elements become paragraphs (block-level) or plain text (inline).
- Whitespace collapses the way the browser renders it; `<br>` is a line break inside the block.
- `script`, `style`, `template`, media no plugin claims (an `img`, `iframe`, `video` or `audio`), form controls and other non-text elements are skipped.
- HTML that yields nothing (only a comment or empty elements) falls through to `text/plain`.

Your own kinds and marks take part in the import the same way. A value-less mark with a `tag` is matched by that tag; a mark with a value needs a `parse` hook:

```ts title="inlineExtras.ts" check
import type { Plugin } from 'edytor';

export const inlineExtrasPlugin: Plugin = () => ({
	marks: {
		// Rendered as <kbd>, exported as <kbd>, and pasted <kbd> elements take it.
		kbd: { tag: 'kbd' },
		// Rendered and exported as <abbr title="…">; pasted <abbr> keeps its title.
		abbr: {
			tag: 'abbr',
			attributes: (title) => ({ title: typeof title === 'string' ? title : undefined }),
			parse: (el) => (el.localName === 'abbr' ? (el.getAttribute('title') ?? '') : undefined)
		}
	}
});
```

A block kind's `parse(element)` works the same way and returns the new block's `data`. Definitions are first-wins, so add hooks to kinds you define rather than redefining a bundled one. See [Custom blocks](/docs/customization/blocks).

## Dragging text

Selected text dragged to another place in the editor moves there, as in Notion: press inside the selection, hold, drag, release where the caret shows. The move is one command, `moveText`, and one undo step that gives back both the text and its place:

1. the range is deleted as a replacement deletes it (`replaceRange`): a range across blocks joins them;
2. its content goes where the drop point is after that deletion, placed as a paste of the same content would place it (`insertFlow`): marks, inline atoms and lines come along, a range across blocks arrives as lines.

The moved text is selected after the drop. Hold <kbd>Alt</kbd> (<kbd>Option</kbd>) at the drop to copy instead: the range stays and a copy lands at the drop point. A drop inside the dragged range changes nothing. A readonly view takes no drop, a kind's own control (a field in a block) keeps its own drags and drops, and dragging during an IME composition does nothing. The drag carries the range as a copy carries it (the Edytor fragment, HTML and plain text), so dropping it in another Edytor or another app pastes it there, and the text stays where it was.

Hooks see `moveText` with its payload (`from`: the range's start and end, `to`: the drop point, both in block offsets; `copy`) and the deletion's planned steps (a copy's: the placement's); `prevent()` keeps everything. Block-handle drags are not text drags: they move whole blocks (see [Block handles](/docs/plugins/block-handles)).

## Plugin hooks

`onCopy`, `onCut` and `onPaste` run before Edytor handles the event. Call `prevent()` to take over; the browser's default is prevented too. For instance (the image plugin does this for you when given an `upload`, with a placeholder while the file uploads and one undo step):

```ts title="imagePastePlugin.ts" check
import type { Plugin } from 'edytor';

export const imagePastePlugin: Plugin = (edytor) => ({
	onPaste: ({ e, prevent }) => {
		const file = e.clipboardData?.files[0];
		if (!file?.type.startsWith('image/')) return;
		prevent(async () => {
			const src = await upload(file); // your upload
			// Add an image block (the bundled image plugin) after the caret's block.
			edytor.selection.state.startBlock?.insertBlockAfter({
				block: { type: 'image', data: { src } }
			});
		});
	}
});
```

`onPaste` runs after the Edytor-fragment check, so it sees pastes from other apps, not copies between Edytor editors. It does not run for <kbd>Shift</kbd>+paste. The first plugin (in plugin order) that prevents wins. See [Plugins](/docs/plugins).

## Pasting a link on an empty line

With the [embed](/docs/plugins/embed) or [bookmark](/docs/plugins/bookmark) plugin listed, pasting one `http(s)` URL (surrounding whitespace aside) on a line that holds nothing writes it as a link, one undo step, and opens a menu under the line, as Notion does:

- **Link** (highlighted) keeps the link. <kbd>Enter</kbd> right after the paste picks it, so it never converts by accident and splits nothing.
- **Embed**, when an allowlisted provider plays the URL, turns the line into an embed of it.
- **Bookmark** turns the line into a web bookmark of it, then asks your `unfurl` for its title.

<kbd>↑</kbd>/<kbd>↓</kbd> move the highlight and <kbd>Enter</kbd> picks it. A conversion is one more undo step: undo gives the linked URL back. <kbd>Escape</kbd>, a press outside the menu, typing, any other edit or a caret that leaves the URL's end close the menu and keep the link. The rows follow the plugin order. A line with text, a <kbd>Shift</kbd>+paste, a `mailto:` link, text that is not one URL, a code block or a void's caption paste as before.
