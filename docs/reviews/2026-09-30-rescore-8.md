## Open units of work

### BW-01 — The horizontal rule turns a block that holds only inline atoms into a divider and drops the atoms

- **Area:** Code organization and elegance (the user-visible effect is an editing behavior)
- **Severity:** medium (the reviewer said low; the verifier raised it)
- **Effort:** S
- **File:** src/lib/plugins/richtext/richTextOperations.ts:121-130 (the virtual-line branch at about :123 and the list-lift branch at :124-130; the root branch already existed at HEAD :117). Compare src/lib/kinds.ts:107 (`holdsNothing`) and :173-205.
- **Failure:** `insertDividerAtSelection` decides emptiness with `block.isEmpty`, which is `!hasContent && !hasChildren`, and `hasContent` counts only non-empty Text parts. `convertToKind` uses `holdsNothing`, which reads `facade.displayLength` and does count atoms. Two examples, both with the caret at offset 0:
  - `ul[li a:@Ann, li c]` with native insertHorizontalRule gives `[divider id=a, paragraph, ul[li c]]`, so the mention is deleted. Turn into Divider on the same seed gives `[ul[li a:@Ann], divider, paragraph, ul[li c]]`.
  - At the root, `[p a:@Ann, p c]` with the horizontal rule also loses the mention.

  This contradicts the function's own docstring ("converting it would silently delete text and children") and reader contract X2. The root case is older than wave 10. Wave 10 copied the same test into the new list-lift branch. Undo restores the atom.

- **Fix:** Build the divider command on one placement helper shared with `convertToKind`. At minimum, replace `block.isEmpty` with the `holdsNothing`/`displayLength` test in both of `insertDividerAtSelection`'s empty branches. Keep the documented list caret rule, which always inserts after the item, and the separate `insertDivider` op name as they are.
- **Done when:** DOM rows show a block holding only a mention keeping the mention under native insertHorizontalRule and under `insertDividerAtSelection()`, both at the root and in a list item, the same as under Turn into Divider. Both paths use one emptiness test.

### BW-02 — A veto on one block in a multi-block Turn into, or in Tab over a selection with gaps, commits the earlier blocks, skips the later ones, and `convertBlocks` returns false

- **Area:** API ease of use
- **Severity:** low
- **Effort:** M
- **File:** src/lib/kinds.ts:227 (`convertBlocks`); src/lib/session/bindings.ts:137-149 (`moveRoots`); src/lib/session/commands.ts (`run`/`dispatch`)
- **Failure:**
  - The plugin is `onBeforeOperation: ({block, prevent}) => block?.data?.locked && prevent()`.
  - On `[p a, p b, p c{locked}, p d]`, selecting b..d and pressing Mod+Alt+1 gives `[p a, heading b, p c, p d]`, with `dispatcher.last` = `{setBlock, applied}`. `convertBlocks` returns false with the same partial tree.
  - On `[p z, p a, p m, p e{locked}]`, `selectBlocks(a, e)` then Tab gives `[z>[a], m, e]` with `last` = `{moveBlock, applied}`. At 35a075d the same Tab refused as a whole.
  - Cause: each target dispatches in its own transact, and a veto inside the `run` scope throws after the earlier steps have committed.
- **Fix:** Build every target's plan first, compose them, and dispatch once, so that a veto refuses everything. Do the same for the moveRoots runs. Or document refusal per block, have each veto skip only its own target, and return applied correctly.
- **Done when:** A row with a locked middle block shows either no change with `convertBlocks` returning false and `last` = refused, or the documented per-block result with a consistent return value. The Tab-over-gaps row agrees. operations.mdx and migration.mdx match the result.

### BW-03 — Turn into places the block for the kind requested before the hook runs, even when a plugin replaces the payload

- **Area:** API ease of use
- **Severity:** low
- **Effort:** S
- **File:** src/lib/kinds.ts:168 (`landingOf`, `lifted`, `next`, `touched` and the `lift` closure are computed from the original `value`, around :160-201)
- **Failure:** A plugin replaces the setBlock payload `{type:'heading'}` with `{type:'list-item'}`. On `ul[a,b,c]`, running `convertToKind(b, Heading 1)` gives `[ul[a], list-item "b" at the root, ul[c]]`. `convertToKind` returns true, but the list-item now sits outside any list. The dispatcher prepares the replaced payload again, but only `prepareSet` reads it. The lift still uses the original kind. operations.mdx:167-177 says "The replacement is prepared again".
- **Fix:** Compute `landingOf`, the liftOut kind and `touched` inside the prepare callback from `payload.value.type`, and from `payload.block` for insertBlockAfter. When the replacement's kind fits where the block is, do a plain setBlock in place.
- **Done when:** A DOM row with the replacing plugin leaves `ul[a, list-item b, c]` intact. A replacement to a kind that does not fit is lifted for that kind.

### BW-04 — The collab DST oracle expects the wrong caret after a remote delete on list shapes, so the documented extensive lane fails at seed 18

- **Area:** CRDT correctness and Collaboration (one shared unit; the fix is in the test harness only)
- **Severity:** low
- **Effort:** M
- **File:** tests/editor-dst/collab-runner.ts:1187 (`seamExpectation`, about :1164-1225); the shape comes from tests/editor-dst/generator.ts:481
- **Failure:** `COLLAB_DST_SEEDS=18 COLLAB_DST_STEPS=60` fails every time at step 33 with `remote-selection-misplaced`. `pnpm test:dst:extensive` runs seeds 1-30 at 60 steps, so the lane documented in docs/editor-dst.md:55 is red. Production is correct in both traced schedules; the oracle is stale in two ways:
  - (A) Minimized schedule. When a dead block has no sibling stop, the oracle falls back to the document's first text (dst-18-b0@0). `sel.seam.slot` says to climb one level instead, and production correctly gives the parent's content end (b_hQ@5).

  `release:check` runs only the default budget, which passes, so releases are not blocked.

- **Fix:** In `seamExpectation`, climb one level when the live parent has no sibling stop. Take the slot from the post-edit placement, or treat promoted descendants as sliding into the slot. Better still, derive the expectation from the replicated slot the way `anchors.ts` `seam()` does. Pin both seed-18 schedules as replay rows.
- **Done when:** `COLLAB_DST_SEEDS=18 COLLAB_DST_STEPS=60` passes, `pnpm test:dst:extensive` is green, and both schedules replay green. Note that the collab spec reads `COLLAB_DST_SHRINK`, not `DST_SHRINK`.

### BW-06 — liftOut re-implements the ZW-03 list split, and landingOf walks the same levels again on the view side

- **Area:** Code organization and elegance
- **Severity:** low
- **Effort:** M
- **File:** src/lib/crdt/edytor-doc.ts:1929 (liftOut :1929-1996 against unNestBlocks' container branch :1877-1904); src/lib/kinds.ts:122-130 (`landingOf`)
- **Failure:** The two algorithms agree today. Each has its own head container (`kindToCopy`/`blockDataOf`), moves the lead items itself, reserves ranks with `ranksFor` and finishes with `emptying`. A change to the split, such as a fix to the ZW-03 race or to which half keeps an ordered list's `start`, must be made twice. Otherwise Shift+Tab and Turn into split the same list differently, and no parity test would catch it.

Do not have unNestBlocks call liftOut, because it takes several ids, uses `settle` and has the adoption branch. Expose the landing levels from the facade so `landingOf` stops recomputing them. As a cheap first step, add a parity test: unNestBlock against Turn into Heading on a middle item.
- **Done when:** One split helper exists, both call sites use it, and a parity row passes.

## Refuted

- **The move keys, a drop or `moveBlocks` leave a bare list-item at the root (CRDT, proposed medium, refuted as a documented design residual).** The behaviour reproduces: Mod+Shift+Up on a first item gives `[p, list-item a, ul[b], q]`. But the contract says a move keeps its kind (docs/editor-delete-contract.md:424 and :498). rescore5-crdt.test.ts:865-868 pins it ("A moved item keeps its kind"), and re-score 6 (docs/reviews/2026-09-30-rescore-6.md:245) recorded it as a residual. Wave 10's only widening applies the same rule to a paragraph stored directly in a list, a shape that arises only from raw JSON, the API or a race. If you want moves to settle the kind to a paragraph, or to the view's flat itemKind as Notion does, it is a product decision. The change would compose `settle` into `moveBlocks` and must also flip the pinned row and contract lines 424 and 498.
- **A concurrent undo of a lift plus a peer's outdent swaps the order of the two items (CRDT, low, refuted).** Running the same steps with no concurrency gives the same result byte for byte: Bob outdents 'b', then Ada presses undo, and the text reads 'pbac'. So the concurrent merge resolves to a valid serialization. The contract only promises order for two concurrent outdents. Undo that puts I1 back at the head of its list cannot also keep 'a' before 'b' once 'b' sits above the list. At most this deserves an optional one-line note on undo.
- **Parts of the divider-duplication finding (Code).** The different caret rule in a list (always after, never split), the separate `insertDivider` op name and the "stale docstring" were refuted as documented design (rich-text.mdx, operations.mdx, S2 decision). The emptiness-test split survives as BW-01.
- **DO/Docs 4403 side claim.** The claim that a lone-surrogate userId used to connect as U+FFFD before wave 10 is doubtful. A non-Latin-1 unencoded header value normally throws. This does not affect BW-07.
