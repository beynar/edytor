# Data model

The replicated document (`src/lib/crdt/`, the doc context): its shape, streams, marks, deletes, operations, the index, roles, seeds, anchors and properties. Layouts and tables have their own file, [layouts-and-tables.md](layouts-and-tables.md); who owns each fact is in the owners table of [AGENTS.md](../../AGENTS.md).

- **Shape.** `JSONDoc = {children: JSONBlock[]}`, `JSONBlock = {type, id?, data?, content?, children?}`, `content` = `JSONText {text, marks?}` and `JSONInlineBlock {type, id?, data?}` (`src/lib/utils/json.ts`). A block owns its inline `content` and its nested `children`; the model is not a DOM mirror.
- **Streams (text ownership).** Each block's text is a stream in a backing text, delimited by boundary items. A split writes one boundary; a merge writes one claim item `{m}` at the end of the gap at the end of the holder's stream (fork patch YP21: among the items of one origin a claim item sorts after content and boundaries, and is never collected, so YATA decides which piece of a concurrent split keeps it: `merge.claim.anchor`). A block's claims are its implicit ones (`id.same.concurrent`), then the claim items of its stream, in text order; the index's rows track claim items as bounds that never delimit, and no read shows them. A split writes the claims that follow its point again at the end of the new block's stream. Split and merge never copy text. `docs/crdt-v14-text-ownership-adr.md` has the details.
- **Marks are paired operations (fork patch YP13).** A mark write is one operation: a start (value, Lamport timestamp, id, side) and an end naming its start; a character shows per mark the open operation with the greatest timestamp (`crdt/text/marks.ts`, `mark.*` rows). Writes stay adjacent to their YATA origins; the integration orders one origin's items left-side marks, content, right-side marks, so a mark's `edge` (document semantics `marks`) decides where a concurrent insert at its ends lands. Local insertions get exactly `marksForInsertion`'s marks (`fitMarks`). They are the engine's only format items (fork patch YP19: no plain format write, no formatting cleanup; a plain item a peer writes is inert).
- **Text deletes are hold records (fork patch YP20).** A text delete appends its writer's hold record to the root `textdel` (in the history's scope): `YNode#delete(index, length, records, fresh)` holds the live units instead of removing them, except those the open undo step inserted (`fresh`, `openSteps` in `crdt/text/model.ts`: removed, so that step's undo changes nothing). A held item reads as deleted (`deleted = removed || holds > 0`); an item shows iff it is not removed and no live record holds it, so a double delete shows again only once both writers undid, in any delivery order. The history's undo deletes the undoer's record (the text shows where it was: nothing is copied), a redo copies the record, an undo of typing holds the typed text (`records.hold(ids)`), a dropped step (limit, a new edit after an undo, `clear`, the horizon) deletes for good what its records hold (`hist.delete-marks.release`), and the purge does so for records older than the horizon. A record whose items have not arrived integrates at once; its hold waits in `store.pendingHolds`. The engine logs every hold-made visibility change in `transaction.holds` (`client, clock, ±len`), which the index folds as edits. Never delete text behind the history's back: go through the facade.
- **Preserve what was not removed (2026-09-28, `docs/editor-delete-contract.md`).** A block delete removes only its members (`del.blocks.promote`: unselected children take the slot; `deleteBlock(id, { keepChildren: false })` is the explicit subtree delete) and a block selection is exactly its members (`sel.blocks.exact`; a selected block that shows only its children — a list, a code block — stands for its subtree: what acts on content — delete, cut, copy, paste, typing, marks, Turn into, `onDeleteSelectedBlocks` — reads `selection.selectedMembers`, while `selectedBlocks`/`getSelectedBlocksInDocumentOrder` are the blocks as clicked, one block to the block menu's Copy link, Move, Duplicate and Escape; marks still skip a closed toggle's hidden body in it).
  - An undo never deletes a block its step created (`hist.undo.withdraw`, the history's withdraw rule): the block is withdrawn and shows while it holds another writer's content.
  - An emptied document writes nothing: each view shows a virtual paragraph (`doc.empty.virtual`) that the first edit in it creates, in the edit's plan.
  - A text range delete that would leave nothing to hold the caret keeps its head block, emptied, with its id, type and data (`del.range.whole-doc`), so peers deleting the whole document keep the same block; it never writes a new one.
  - A range inside one `lines` island (a code block's whole text) keeps its head the same way (`del.range.island-kept`); other islands keep `del.range.empty-container`.
  - A block-set delete and the block menu's Delete share `caretAfterBlockDelete` (`replaceSelection.ts`): the start of a promoted child that takes the set's place, else the end of the nearest line before, else the start of the nearest line after; Escape ends the first selected block's `shownText` (`selectedBlocksExit`; the one shown-line walker, also behind `selectLines`, Mod+A's and a triple click's range).
  - Never `firstEditableText` (it stops at an inline atom).
- **Module layout.** `crdt/edytor-doc.ts` is the facade's wiring (`docFacade`): each part is a `crdt/doc/` module over an explicit context, the parts before it (`reads`, `capability`, `funnel`, `events`, `history`, `anchors`, `steps`, then the op families `moves`, `layout`, `split-merge`, `delete`, `meta` and `content` over `OpsContext`; range deletion and flow placement compose that same context with the ops they call). The placement model (`crdt/placement/model.ts`) and the text model (`crdt/text/model.ts`) are plain functions over the vendored engine (`engine.js`), imported where they are used; only the public binding (`bindDocModel`, `bindCrdt(Y).doc`) lists them as objects (`model`, `text`, `runs`) and on its facades, with the from-scratch ownership (`computeOwnership`, the index's oracle), so an editor's graph ships none of what only the room, tooling and tests read; a test reaches them by importing the functions. DEV-only checks are module functions called under `DEV`, never class methods (a production build drops them). The index (`crdt/text/runs.ts`) is wired the same way from `crdt/text/index/` parts over one shared state object (`state.ts`): `claims`, `streams` (with each block's claims), `layout`, `placement`, `records`, `cache`, `fold`, `report` and `checks`. A fix goes in the part that owns the fact, never in a second part.
- **Operations are two-phase.** Every facade op is `apply(prepare.op(…))`. `prepare` writes nothing and returns a plan of named steps with its effect (or `refused`); `apply` writes it in one transaction and returns `OpResult {status: 'applied' | 'noop' | 'refused', ids}`. Range delete (`prepare.deleteRange`/`replaceRange`/`deleteBlocks`) and paste/drop placement (`prepare.insertFlow`) are single plans whose rules are rows in `docs/editor-delete-contract.md` (`del.range.*`, `flow.*`). A pasted line whose kind joins no text (a list, a code block, a void) is placed as a block, never joined, so no text lands where nothing shows it (`flow.apart`; assert it in DOM tests with `expectNoHiddenContent` from `src/tests/fixtures/dom/invariants.ts`), and a code line takes a flow as plain lines (`flow.lines`). A new structural case means a new contract row, not a caller flag.
- **One index, one report.** `facade.onChange(cb)` delivers one `DocChange` per commit that changed the visible document (`added`, `removed`, `moved`, `meta`, `content`, `order`).
  - The index folds a commit on the document's `commit` event (fired once per transaction, before `afterTransaction`) when the registry or a node under it changed (`changedUnder`, `crdt/structs.ts`); the engine's nodes have no observers (fork patch YP19), and the history captures by the same test over its scope.
  - Nested transactions publish once; a transaction that nets out publishes nothing.
  - Its callbacks (and `onWritableChange`'s) run inside the engine's `update` emit: one that throws is logged, never rethrown (an error escaping that emit wedges the doc: no later transaction emits `update` again).
  - A read folds every transaction whose writes are in the document and whose commit fold has not run (the open one, and one an `update` listener or observer started, whose body runs before its observers), so a report or read in between never mixes their items with an index that has not seen them; such a write's effects can then appear in the report of the transaction whose cleanup started it.
  - Each backing text keeps a maintained row (`crdt/text/rows.ts`): an edit that writes or removes no boundary moves it by its units, never a rescan.
  - The claim graph, placements and children index are maintained too: a structural change re-decides the owners its claims reach, the placements of the blocks whose slot, record or mover changed (the fold reads the sequences a commit touched and the engine's `transaction.moves`), and the slots of the stored subtrees whose slot walk reads a changed block, patching only those parents' child lists (each replaced, never mutated under a reader) and re-running the layout rules only on the layouts it reaches; a placed block's order key comes from its sequence neighbours (`placement/keys.ts`), never from a walk of the parent's sequence, and a cycle through a changed display edge is resolved locally: the block whose edge is the cycle's oldest falls back to its next candidate (no global pass).
- **Roles.** `void` (structurally isolated, not editable by the core flow), `island` (editable, sealed from its neighbours) and `layout` (items side by side, below) drive merge, unnest, delete and navigation.
  - They are not cosmetic.
  - A document learns them from its views' plugins or from its `semantics`: `createDocument`/`loadDocument` default to `defaultSemantics` (as the room does; `semantics: {}` checks none), `attachDocument` (a view's own document) to none.
  - The bundled rows live in `crdt/semantics.ts` (`richTextKinds`, `codeKinds`, `imageKinds`, `layoutKinds`, exported): change them there, not in the plugins.
  - An app's own kinds have one source the same way: one table spread into the kind records and passed to `semanticsOf` (which reads only a record's structural fields) and `mergeSemantics` (field by field, `SemanticConflictError` on a disagreement) for the room.
  - In development builds a document publishes `semanticsDigest` of its roles in its presence and the room logs the kinds it reads otherwise (`semanticsMismatch`, log entry `semantics`).
  - An island whose role also says `lines: true` (code → `codeLine`, opt-in) holds only lines and a line holds no children, even a deleted one's children take the island's slot; the display enforces this against undo and concurrency (`displaySlotOf`, the index's `typeOf`, line kinds from the roles via `EdytorDocConfig.kinds`; `docs/editor-delete-contract.md` `conc.island-lines`).
  - Any other island keeps its structure (a retype to an ordinary kind re-kinds only a lines island's lines, as `typeOf` does).
  - Nothing merges into a block that renders no content (`canMerge`: a code block's first line, a list's first item, a row's first cell), and a container (no content, not an island: a list, a row) never merges as a whole: the key merges and text ranges act on its items, no key, block delete or move leaves one with no child, an outdent splits it rather than handing its later items to a paragraph (the list keeps the items after the outdented ones; a new list takes those before), nothing is retyped into a kind that renders no content, and a peer's item promoted out of a removed one shows as its new parent's default child at read time.
  - One predicate owns what a container holds, `fits(parent, kind)`: a container whose default child is its own kind (a list's `list-item`, a columns layout's `column`) holds only those and containers of them, one whose default child is the document's (a column) holds anything; moves are refused where blocks do not fit (`canPlace`), Tab nests under a container's last item (`nestParent`, also `moves.ts` `inside`), outdents/lifts are refused where they would not fit, and a plain (default-kind) block shed or pasted into a list becomes its item, while any other kind keeps its kind and data, as read-time promotion does (`settledKind`/`fitted`); the move command's `out` step asks `prepare.unNestBlocks`, not `canPlace`; explicit `insertBlocks`/retypes are not refitted, though a plain block stored directly in a list shows as its item at read time (`typeOf`'s `itemOf`: no race leaves a bare paragraph in a list; a Turn into racing an outdent may leave another kind, such as a heading, there, as a merge can — a documented residual) (`isContainer`, `fits`, `settle`, `emptiable`/`emptying` in the facade — `rangeDelete.ts` uses the same ones; `container` reset in `displaySlotOf`/`typeOf`; `del.merge.container`).
- **Placement (fork patch YP22).** Each data owner keeps one order sequence, its node's list part: a block's children are home slots `{ b: id }` there (the top-level blocks' in the registry root's list part), written once at the block's creation right after its left sibling's unit (YATA's origin rule: later inserts there stay together, `order.insert.run`; among the slots of one origin the origin writer's own sort first), and a move is one move record (`ContentMove`, content ref 12) in the destination's sequence naming the moved blocks' home slots in order, with a Lamport priority (one per writer until it sees a peer's record: a writer's gestures win or lose together), a side (`0` after what precedes it, `1` before what follows: `moveTo`'s `side`), the chain it stands at (`at`: the home slots from the root down to the block it stands at — by default the first moved — named by the writer, `placement/model.ts` `unitChain`; home slots never move, so every writer names one chain for one block) and its part there (`PART`: a head, kept blocks, a head with the block, the block, blocks after it). Two records at one origin sort by class, then by their chains level by level (`sourceOrder`; a record waits for its chain, so no document hook and no integration order decides), then by part, then the stronger first: the order every serial run of a split, an outdent and a lift into one gap gives (`del.merge.container`). A split-born block's slot carries its boundary's id (`BlockSlot.s`): the slots of one origin sort by their boundaries' order in the text (`order.split.text`, no read-time permutation), before slots no split made, then the origin writer's own first (`extendsRun`, read from ids and the parent node, never from content), then by client id; a collected slot keeps its key. A slot shows at the record that wins its movers — the greatest `(priority, client, clock)` — and reads as deleted at home; deleting a record (an undo) hands the slot to the next record, else home; a delete mark or a hold beats a move (`gone`). A block's candidate edges are its live records, strongest first, then its home slot (`candidatesOf`); the index accepts every candidate greedily in descending stamp order, each block at the first that closes no cycle: the later move wins, and the block a cycle drops is back where it stood before that move (its next record, else home; at the root's tail, by stamp, only when every candidate closes a cycle): one block at a time (`text/index/placement.ts` `settle`; a cycle drops its oldest edge, `retryFallen` lets a dropped block rise again), for an edit and for the first build alike — the stable state is unique, whatever the order — and the tests' greedy rebuild (`src/tests/oracles/placements.ts`) is what the self-checks compare it with. The writes anchor where the index shows a block and carry only the units it shows at a record (`anchorIn`, `shownIn`): a unit a cycle sent back is never re-asserted by a neighbour's write. No rank is stored anywhere: the index keeps an order key per child in memory (`placement/keys.ts`: `keyBetween` a child's neighbours, `promotedRank` a promoted child's, `claimedRank` a merged-away block's children after the owner's own, `cellKey` a table's cells by column). Reads: one walk over an item's units (`unitsOf`: the engine's display, `shownBy`; the places, `positionsOfItem`; what the index shows, `shownIn`), `entriesOf` (a sequence as displayed), `anchorOf` (where a slot shows as the engine stands), `positionsOfItem` and `slotsBefore` (the places a block can show at, and those before it, nearest first: the cost of the gap to the nearest shown block); writes: `placeAfter` (a slot or a record after a displayed entry — one in the middle of a record's display carries that record's later units along, so the new entry shows between them), `removeUnit`. The purge drops the old records no block shows at and the slots of removed blocks. Schema generation 9 (wire word `14009`) was the cutover; the stored encoding is generation 10's (below).
- **Read-time display.** A deleted block's unmarked children, and a child a peer adds, moves or splits under it concurrently, show in its slot (`displaySlotOf`, key `promotedRank`); a block shown under its parent's claim owner (the parent merged away, or promoted out of a block deleted inside it) is keyed in the owner's claimed space (`claimedRank`), since the index's order keys are local to a replica (`placement/keys.ts`) and a children list compares one key space only; nothing hides with a deleted subtree (`del.blocks.promote`), and the delete writes no move (the children keep their home slots; the plan's `effect.moves` lists none). A void kind displays no children: a retype to void writes no move either, its children and a child that lands under one concurrently show in its slot, from the document's roles (`DisplayOwnership.childless`, fed by the runs index from `roleOf`), so replicas must hold the same roles. A dissolving layout and a deleted layout item are read the same way (`layout.single`, `layout.only-items`): a reader without the layout role sees their blocks in the layout.
- **What is stored (schema generation 10, wire word `14010`; fork patches YP24–YP29, `docs/archive/storage-diet/design.md`).** A block node holds `n`, `type`, `l`, its data leaves, its `del.`/`wd.` marks and, for a block with its own text, `content`; its id is its registry key (an atom's node keeps its own `id`), and its attribution record on `blockattr` is keyed by the block's id too. The update encoding (upstream's columnar v2, YP17) writes each distinct string once per update (YP24: map keys, root and node names, string values and object keys through one table, so a block's id costs one string however many entries name it), each client id once (YP26: an index after its first use, in the client column and the delete set), a paired mark's value in parts (YP25: its operation id only where it is not the item's own, its start only as a distance from the end), the parent kind in the info byte (YP27), integers past 31 bits as varints and a `[client, clock]` pair through the client table (YP28: nonces, split keys), and a collected mark or claim as its sort class alone (YP29, content ref 13). The update's first varuint says the encoding (`1`): an upstream update, or one of generations 6 to 9, is refused before it is decoded (`an update of another encoding`), never converted. Measure a change to the stored shape with `node bench/stored-size.mjs` (what each kind of struct costs, by ablation, raw and gzip).
- **Seeds.** A seed is written under a writer id hashed from the value, in a band below 2^26; live writers are uint53, so a seed never displaces a live block. Two different seeds sharing an id resolve by hash order (irreversible), so never seed a changing snapshot beside a room. The derived own-text writer is a different id space (53-bit `hash53`); never widen the seed writer.
- **Anchors** are `DocAnchor = {b, a}` (see the anchor contract in [selection-and-input.md](selection-and-input.md#selection-contracts-that-must-not-regress)).
- **Properties (data).** A block's, an atom's and the document's (root `docdata`, in the history's scope) `data` is one attr per JSON leaf, `d/` + RFC 6901 pointer (`crdt/data.ts`): per-leaf LWW, a primitive leaf under which leaves exist reads as the object.
  - Arrays are fine-grained (`Y.Array` semantics, no Y types): a `[]` marker leaf plus items, item `id`'s value under segment `~id` (`~` + a letter is never an escape), and its existence and place its slot `{ p, i }` in the owner's one order sequence (the node's list part, fork patch YP22; the first live slot of an id counts: two peers adopting one array write two); an item lives while a live slot of its id does, so a remove (its slots and leaves deleted) beats a concurrent inner edit or move (orphan leaves are skipped); an insert goes right after the item before it (YATA's origin rule, so a client's later inserts there stay together even across commands) and a move is a move record; a whole-array assignment keeps the items a longest common subsequence keeps equal and pairs the rest by position (`arrange`; `common` is linear: the equal prefix and suffix, then an exact Hunt–Szymanski run while at most `PAIRS_BOUND` pairs of equal values compare, else the middle pairs by position; never a full LCS table); `order` moves only what leaves the longest increasing run. A patch's writes (`DataWrite`) are its leaf writes and its slot writes (`insert` after an item, `move`, `remove`), applied by `writeData`.
  - Patches address items by index or id (`~…`), resolved at prepare time (the plan's leaf writes name ids; a gone id is refused); `facade.dataItemIds(target, path)` lists them; a write that names an item by id stays on it wherever collaborators move it (a keyed `{#each}` row).
  - An array assigned where no item is (a new node's data, a converted next.6 array leaf, a whole assignment) takes ids derived from its index and its value's hash (`~l<i>.<hash>`: identical concurrent assignments and seeds write the same items, different ones stay apart), its slots written in order (a converted leaf's by the first write through it); inserts into an array with items use `randOf(doc)`.
  - A leaf holding a non-empty object or array (an atomic path's, a next.6 array) reads as its keys or derived items (`closed`, `open`); a patch opens it only along its path, and `patchWrites` writes every leaf that differs from the stored ones (a next.6 array is converted into items by the first op through it; two peers' concurrent first ops converge, a set of an item may lose to the other's conversion). The whole `data` attr of documents before next.6 is not read (`DATA`: only the room's purge deletes it).
  - A kind's role may declare `atomic` paths (`data.atomic`: `BlockRole.atomic`, adopted with the role so every replica agrees): a write at or under one writes its whole value as one leaf (`collapse`) and deletes the leaves under it, so concurrent assignments never merge into a hybrid; an object leaf reads as its keys.
  - One write path: `prepare.patchData(target, ops)` (`target` a block id, `{block, atom}` or `null`; ops `{path, value?}`, `{path, splice}`, `{path, order}`; `setBlockData`/`setInlineData` and a flow's `redata` are root patches; `setBlock`'s data — a retype's, Turn into's — sets the leaves it names and removes none, `data.retype.keep`).
  - The index folds leaf attrs as `meta`; the doc root's change is `DocChange.data`.
  - `JSONDoc.data` is seeded (joins the seed hash only when present; hashed and built from the key-sorted form, so key order never splits a seed) and exported by `toJSON` only when non-empty.
  - View: `block.data`/`atom.data`/`edytor.data` are deep proxies (`crdt/props.ts`: reads through the cell (blocks, atoms) or `docData()`, a proxy cached per path, an array item's path by its id; a set, a delete or an array method is the patch of only what it changes: `push`/`pop`/`shift`/`unshift`/`splice`/`length` one `splice`, `sort`/`reverse` one `order`, an equal value nothing). The view queues one task's patches per target (`session/props.ts` `DataWrites`), reads them back through `dataPreview` (a queued new item has no id: named by index), and dispatches them on the next microtask, or first thing in `Dispatcher.operate` and a history replay, as one `patchData` per target (several targets: one `run`, one `transact`); a view that does not `permit` dispatches at once (refused, no throw). `document.data` is the same proxy with raw writes. All writes are the view's `patchData` operation (hooks see every data write, `setBlock`'s included, as a `patchData` step); the dispatcher lets a `patchData` setting only strings at the same target and paths continue the previous one's undo step when each new string inserts or deletes one run in the previous one (`typedFrom`: typing into a bound field); a flag, number, delete, object, or a string set to another value (`'todo'` → `'done'`) is its own step.
  - A kind's own control inside the host (any native form control, whatever its type, or a nested foreign editable, never the root or a text element: `isKindControl`) owns every event on its composed path (`ownsEvent`): keys, `beforeinput`, paste, copy, cut, drops (a file is swallowed) and selection, whatever the selection, a block selection included.
  - `onKeyDown` (before the readonly and hotkey paths), `onBeforeInput` (`isBrowserOwnedNativeInput`, before the selection sync), `onPaste`, `copySelection`, `onDrop` and the projector ask that one predicate; never add a per-type or per-handler check beside it.
